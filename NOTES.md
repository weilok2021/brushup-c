## Findings
- 2026-09-05, LeakSanitizer misses leaks at -O0. User's lesson-1 program with `free` removed ran silent under `-fsanitize=address`; valgrind reported 16 bytes definitely lost. Cause verified: stale copies of the pointer in dead stack frames are picked up by LSan's exit-time stack scan, so the block counts as reachable. Reported correctly at -O1 or after scrubbing the stack. Decision: ASan stays for overflow/UAF (immediate, precise); leaks are checked with valgrind via a `make check` target on a plain build. Makefile template updated in lesson 1, reference sheet and the user's exercise folder.
- 2026-09-05, `malloc(n * sizeof ptr)` (pointer instead of pointee) is silent under `-Wall -Wextra` with gcc 13; only the run catches it, and only when the block is then overrun. Chosen as lesson 2's first planted bug for that reason. `struct rect` was given four ints (16 bytes) so the bug is visible; a two-int struct is 8 bytes, the same as a pointer, and the bug would have been silent at runtime too.
- 2026-09-12 (lesson 4 in progress): first draft of `word_replace` looped over slots with a `sizeof` length guess, freed characters one by one, and stored the borrowed `replacement` pointer. Discussed: a `char**` carries no length (count, sentinel, or contract), a heap block is freed whole by its start pointer, and "heap copy" means the slot must own a fresh block. The user said the pattern of a finder returning a slot address, instead of an index used in a later loop, is new to them and asked for time to digest. Reinforce this "return the address of the thing to change" pattern in lesson 10 (`Node **`) rather than assuming it.
- 2026-09-12 (lessons 8, 10, 11, 12 authoring): LeakSanitizer at -O0 DID report the planted leaks in these lessons (for example the missing `free(scratch)` in `merge_sort`, 32 bytes), unlike the lesson 1 leak. Difference: the only copy of the leaked pointer lived in a frame that later calls overwrote, so the exit-time stack scan found no stale copy. The lesson 1 pointer lived in `main`'s frame, which stayed intact. Conclusion unchanged: LSan at -O0 is unreliable either way; `make check` (valgrind, plain build) stays the leak gate, and the lessons say so.
- 2026-09-12 (lesson 9 authoring): forcing `realloc` failure with `SIZE_MAX` trips gcc `-Walloc-size-larger-than=` and a valgrind "silly arg" error; `(size_t)1 << 62` is below `PTRDIFF_MAX`, warning-free, and valgrind returns a clean NULL. The ASan build aborts on the request instead (default `allocator_may_return_null=0`), so the experiment is plain-build only.
