Scan, Stop, Swap

Quicksort's partition and merge sort's merge are plain loops with one invariant each. Write both, prove each with a checker, and run one level of quicksort by hand. Lesson 8 only adds the recursion.

About 45 minutes Where: WSL, exercises/07-partition/ Mission · Cheat sheet · Lesson 6
Your win today. Write partition and merge from a blank file, without recursion, each proved by a postcondition checker you also write, and see for yourself why the scans must stop on equal keys and where the one bounds guard has to sit.

The promise a partition makes

Take 9 4 15 9 26 5 35 4 and call the first value, 9, the pivot. A partition rearranges the range so that every value left of the pivot is no larger than it, and every value right of it is no smaller. One correct result is 5 4 4 9 26 9 35 15, with the pivot at index 3. Neither side is sorted. But look where 9 sits in the fully sorted array, 4 4 5 9 9 15 26 35: index 3. The pivot is already in its final place and never moves again. That is the promise, and it is exactly what a sort needs: put one value where it belongs, then deal with the two sides separately.

Sedgewick and Wayne, 2.3 Quicksort: after partitioning, “the entry a[j] is in its final place in the array, for some j”. Cited as evidence; the reading list below is C.

Write the promise down as a postcondition and it becomes a function you can test: partition(a, lo, hi) returns the pivot's final index p, with a[lo..p) <= a[p] <= a[p+1..hi). A checker is two loops:

int is_partitioned(const int* a, size_t lo, size_t hi, size_t p) {
    for (size_t k = lo; k < p; k++) {
        if (a[k] > a[p]) {
            return 0;
        }
    }
    for (size_t k = p + 1; k < hi; k++) {
        if (a[k] < a[p]) {
            return 0;
        }
    }
    return 1;
}

Lesson 5's is_sorted played the same role. Every exercise prints at least one line a function computed about the result, not one you read off the screen.

Two scans that stop

The pivot stays parked at a[lo] while two indices scan the rest of the range towards each other. At every moment the range looks like this:

lo        lo+1 .. i-1        i .. j        j+1 .. hi-1
[ pivot ] [ known <= pivot ] [ unknown ] [ known >= pivot ]

i walks right and stops on a value that is not smaller than the pivot. j walks left and stops on a value that is not larger. Everything i has walked past is <= pivot; everything j has walked past is >= pivot. That is the invariant. When both have stopped and i < j, the two stopped values are each on the wrong side, so swap them and step both indices inward. When i >= j, the unknown region is empty: the scans have crossed. Then a[j] is <= pivot, so swapping the pivot into slot j keeps both sides honest, and j is the answer.

pivot 9      9  4  15  9  26  5  35  4
i=1 j=7      i stops at a[2]=15; j stops at a[7]=4          swap
             9  4  4  9  26  5  35  15
i=3 j=6      i stops at a[3]=9  (equal to pivot: stop!)
             j stops at a[5]=5                              swap
             9  4  4  5  26  9  35  15
i=4 j=4      i stops at a[4]=26; j walks 35, 26, stops at a[3]=5
             i=4 >= j=3: crossed, stop
swap a[lo] with a[j]:
             5  4  4  9  26  9  35  15
             ^ <= 9 ^  [9]  ^ >= 9 ^          return 3
/* Partition a[lo..hi) around the pivot a[lo]. hi - lo must be at least 1.
   Returns the pivot's final index p: a[lo..p) <= pivot <= a[p+1..hi). */
size_t partition(int* a, size_t lo, size_t hi) {
    int pivot = a[lo];
    size_t i = lo + 1;              /* scans right, stops on >= pivot */
    size_t j = hi - 1;              /* scans left, stops on <= pivot */
    for (;;) {
        while (i < hi && a[i] < pivot) {
            i++;
        }
        while (a[j] > pivot) {
            j--;                    /* a[lo] == pivot stops this at lo */
        }
        if (i >= j) {
            break;
        }
        swap_ints(&a[i], &a[j]);
        i++;
        j--;
    }
    swap_ints(&a[lo], &a[j]);       /* pivot into its final slot */
    return j;
}

This is Hoare's scheme, the two-scan form. The language-free pseudocode reads do i := i + 1 while A[i] < pivot, do j := j - 1 while A[j] > pivot, if i >= j then return j. The one-scan form, Lomuto's, walks j once and keeps a boundary i; it is easier to write and does about three times as many swaps. This course uses Hoare's because lesson 8 and Weiss's sort.c do.

Wikipedia, Quicksort, Hoare partition scheme: “When eventually the pointers cross (the first points after the second), no exchange is performed; a valid partition is found.” Hoare's scheme “does three times fewer swaps on average” than Lomuto's.

Stop on equal keys

The line marked stop! in the trace is the one people get wrong. It looks harmless to let i skip a value equal to the pivot: it is not out of place. Run six equal values and watch where the pivot lands:

7 7 7 7 7 7   scans stop on equal keys     pivot lands at 3   (the middle)
7 7 7 7 7 7   i skips equal keys           pivot lands at 5   (the end)

With the stops, i and j halt at every element, swap sevens with sevens, and meet in the middle. Without them, i runs to the end of the range and the pivot is placed there, leaving a range of five on one side and none on the other. Do that at every level and a sort of n equal keys does about n²/2 compares. Sedgewick and Wayne: “It is best to stop the left scan for items with keys greater than or equal to the partitioning item's key and the right scan for items less than or equal to the partitioning item's key”. The test data has two 9s and two 4s, and a block of six 7s, so that you can see both stops happen.

Sedgewick and Wayne, 2.3 Quicksort. Hoare's scheme with these stops gives a balanced split even when every key is equal (Wikipedia).

One guard, one free pass

Two size_t details, and they are not symmetric. The i scan needs i < hi: when the pivot is the largest value in the range, as in 9 1 2 3, every value after it is smaller and nothing stops the scan before the end of the block. The j scan needs no j > lo guard because the pivot itself sits at a[lo], and a scan that stops on values <= pivot cannot walk past it. Choose the pivot from anywhere else and that free pass is gone. Weiss avoids both guards by parking chosen stoppers at each end first; you will read how below.

Also from size_t: j = hi - 1 is only meaningful when the range holds at least one element, which is why the header says so. Lesson 8's recursion will never call partition on a range shorter than two.

You are the recursion

Quicksort is: partition, then sort the left side, then sort the right side, by the same method. Do one level of it by hand in main, with no recursion at all. Partition the whole range; the pivot 9 lands at 3. Partition the right side [4, 8); the pivot 26 lands at 6. Partition the left side [0, 3); the pivot 5 lands at 2:

[0, 8)   9 4 15 9 26 5 35 4     pivot 9   ->  5 4 4 [9] 26 9 35 15    p = 3
[4, 8)   26 9 35 15             pivot 26  ->  15 9 [26] 35             p = 6
[0, 3)   5 4 4                  pivot 5   ->  4 4 [5]                  p = 2
                                              4 4 5 9 15 9 26 35

Three values are in their final places and the array is nearly sorted. Two ranges are still unsorted, [4, 6) holding 15 9 and the single-element ranges that need nothing. Lesson 8's quick_sort_range is the function that keeps going: it calls partition and then calls itself on [lo, p) and [p + 1, hi), both strictly smaller, until every range has fewer than two elements. That is lesson 6's rule 2 with p excluded from both sides.

Merge: take the smaller head

Merge sort's step is the other way round: the two halves are already sorted, and one pass combines them. Walk both runs with one index each, always copying the smaller head into a scratch area; ties take the left run, which keeps equal keys in their original order. When one run is used up, copy the rest of the other:

left  a[0..4) = 4 9 9 15      right  a[4..8) = 4 5 26 35
i=0 j=4   4 < 4 ? no   take left   scratch[0] = 4     i=1
i=1 j=4   4 < 9 ? yes  take right  scratch[1] = 4     j=5
i=1 j=5   5 < 9 ? yes  take right  scratch[2] = 5     j=6
i=1 j=6   26 < 9 ? no  take left   scratch[3] = 9     i=2
i=2 j=6   26 < 9 ? no  take left   scratch[4] = 9     i=3
i=3 j=6   26 < 15 ? no take left   scratch[5] = 15    i=4   left run empty
          copy the rest of right   scratch[6] = 26  scratch[7] = 35
          copy scratch[0..8) back into a[0..8)

The invariant: scratch[lo..k) holds the k - lo smallest values of both runs, in order. Each step extends it by one, because the smaller of the two heads is the smallest value not yet taken.

/* Merge the sorted runs a[lo..mid) and a[mid..hi) via scratch[lo..hi). */
void merge(int* a, size_t lo, size_t mid, size_t hi, int* scratch) {
    size_t i = lo;                  /* next unused in the left run */
    size_t j = mid;                 /* next unused in the right run */
    size_t k = lo;                  /* next free slot in scratch */
    while (i < mid && j < hi) {
        if (a[j] < a[i]) {
            scratch[k++] = a[j++];
        } else {
            scratch[k++] = a[i++];  /* ties take the left run */
        }
    }
    while (i < mid) { scratch[k++] = a[i++]; }
    while (j < hi)  { scratch[k++] = a[j++]; }
    for (k = lo; k < hi; k++) {
        a[k] = scratch[k];          /* copy back exactly [lo, hi) */
    }
}

Who owns scratch? Not merge: it receives the pointer, writes through it and never frees it, a borrower in lesson 3's terms. In this exercise main allocates one block of eight ints and frees it. Lesson 8 moves that owner into a merge_sort wrapper so that main never learns the block exists; the merge function itself does not change.

The interface

partition.h

#pragma once

#include <stddef.h>

/* Exchange the two ints at a and b. */
void swap_ints(int* a, int* b);

/* Return 1 if the n ints at a are in ascending order, else 0. */
int is_sorted(const int* a, size_t n);

/* Rearrange a[lo..hi) around the pivot a[lo]. The range must hold at least
   one element. Returns the pivot's final index p, with
   a[lo..p) <= a[p] <= a[p+1..hi). */
size_t partition(int* a, size_t lo, size_t hi);

/* Return 1 if a[lo..p) <= a[p] <= a[p+1..hi), else 0. */
int is_partitioned(const int* a, size_t lo, size_t hi, size_t p);

/* Merge the sorted runs a[lo..mid) and a[mid..hi) into ascending order,
   using scratch[lo..hi) as workspace. scratch is borrowed, never freed. */
void merge(int* a, size_t lo, size_t mid, size_t hi, int* scratch);

Five functions, all public here because main drives them directly. In lesson 8 partition and merge become static helpers behind quick_sort and merge_sort; the code inside them is the code you write today.

Reading the three reports

1. Skipping equal keys. No report, and every checker still says yes: the postcondition allows equal keys on either side. What moved is the pivot's landing spot. The first line becomes pivot 9 lands at 4, and the six 7s give pivot 7 lands at 5: the end of the range, a five-and-zero split instead of three-and-two. A correct partition can still be a bad one. The checker cannot see that; only the landing index can.

2. The missing guard. The 9 1 2 3 call walks i past 1, 2 and 3 and reads the int after the block:

ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000020 ...
READ of size 4 ...
    #0 ... in partition partition.c:23
    #1 ... in run_partition main.c:33
    #2 ... in main main.c:56
0x502000000020 is located 0 bytes after 16-byte region
allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in copy_of main.c:14

Sixteen bytes is four ints: the small block, not the eight-int data. The same shape as lesson 1's off-by-one, reached by a scan with no stopper instead of a loop bound. The first three partition lines printed fine before it; their ranges all had a value >= pivot somewhere after the pivot.

3. The right run's tail never copied. Under the sanitizer build:

merged: 4 4 5 9 9 15 -1094795586 -1094795586
sorted: no

The loop copied the six values it compared, then stopped when the left run emptied. scratch[6] and scratch[7] were never written, and the copy-back moved whatever malloc left there into a. Under ASan that is the byte 0xbe repeated, which reads as -1094795586; on the plain build it is anything. Valgrind names the problem, not the fix: “Conditional jump or move depends on uninitialised value(s)” inside printf, called from your print helper. When Valgrind blames printf, ask which value you handed it and where that value should have been written.

Read next

Everything here is C or language-free. Read in this order.

  1. Partition in C, without guards. Mark Allen Weiss, Data Structures and Algorithm Analysis in C, 2nd ed., sort.c, the functions Median3 and Qsort (free from the author's source files page). His scans are while (A[++i] < Pivot) and while (A[--j] > Pivot) with no bounds test at all, because Median3 has already parked a value <= pivot at Left and the pivot itself at Right - 1. Compare that with your one guard and one free pass. The file also keeps a broken scan under #if 0, labelled as code that does not work; start both scans on a value equal to the pivot and see why.

  2. Merge in C, a different shape. Aspnes, 5.3.4 Mergesort, the merge function only. It merges two separate arrays a1 and a2 into out with one loop and a compound test, where yours merges two runs of one array through scratch with three loops. Same invariant. Leave the recursive part for lesson 8.

  3. The two schemes, language-free. Wikipedia, Quicksort, Hoare partition scheme and the Lomuto partition scheme just above it. Pseudocode plus the sentences on crossing pointers and equal keys. Ten minutes, and enough to recognise either scheme when you meet it in someone else's C.

  4. If you prefer to watch first. CS50 Short, Merge Sort (Doug Lloyd), for the merge step traced by hand.

Where this lands in CS107. Lecture 8 (Generic Operations) assigns the library qsort, which needs a comparison function but no partition from you*. Writing one yourself once is what makes its size_t nmemb, size_t size interface readable later.
