Shrink, Then Trust

A recursive function answers the smallest range outright, hands every other range on one size smaller, and trusts the answer that comes back. Four small functions, one array, and a debugger view of the frames.

About 40 minutes Where: WSL, exercises/06-recursion/ Mission · Cheat sheet · Lesson 5
Your win today. Write four recursive functions over a half-open range [lo, hi) from a blank file, each in a different shape (shrink by one, work on the way back up, halve, halve and keep one side), watch their frames in gdb, and recognise the two sanitizer reports that mean a recursion never shrank.

Two rules and one act of trust

Eight ints sit in a heap block: 9 4 15 9 26 5 35 4. Ask for the sum of the range [0, 8). A loop would walk it. A recursive function says instead: the sum of [0, 8) is a[0] plus the sum of [1, 8). And the sum of [1, 8) is a[1] plus the sum of [2, 8). The chain ends at [8, 8), the empty range, whose sum is 0 with no call at all:

sum [0, 8) = 9  + sum [1, 8)
sum [1, 8) = 4  + sum [2, 8)
sum [2, 8) = 15 + sum [3, 8)
sum [3, 8) = 9  + sum [4, 8)
sum [4, 8) = 26 + sum [5, 8)
sum [5, 8) = 5  + sum [6, 8)
sum [6, 8) = 35 + sum [7, 8)
sum [7, 8) = 4  + sum [8, 8)
sum [8, 8) = 0                     empty: answered without a call
long sum_range(const int* a, size_t lo, size_t hi) {
    if (lo == hi) {
        return 0;                     /* base case: the empty range */
    }
    return a[lo] + sum_range(a, lo + 1, hi);
}

Two rules make this finite. Rule 1, the base case: some range is answered without calling. Here it is the empty range. Rule 2, shrink: every other call receives a range that is strictly smaller. Here [lo + 1, hi) has one element fewer than [lo, hi). Aspnes lists the two ways this goes wrong, under the headings “Omitting the base case” and “Failure to make progress”. Break either rule and the calls never stop.

Aspnes, Yale CPSC 223 notes, 5.3.2 Common problems with recursion. On the missing base case: “This is the recursive version of an infinite loop.” On failing to make progress: “we thought we were recursing on a smaller instance of the problem, but in fact we weren't.”

Then the act of trust. While writing the line a[lo] + sum_range(a, lo + 1, hi), do not trace the inner call. Assume it returns the correct sum of the smaller range, and write the one step that turns that into the sum of the whole range. That assumption is safe exactly when the two rules hold, because the smaller range is closer to the base case, which you did write by hand. Shrink, then trust.

Every call gets its own frame

Each call to sum_range is a new stack frame with its own copies of a, lo and hi. The pointer copies all hold the same address, so every frame reads the same heap block; only lo differs. Stop the program under gdb when lo is 3 and ask for a backtrace:

(gdb) break sum_range if lo == 3
(gdb) run
Breakpoint 1, sum_range (a=0x503000000040, lo=3, hi=8) at recur.c:6
(gdb) backtrace
#0  sum_range (a=0x503000000040, lo=3, hi=8) at recur.c:6
#1  in sum_range (a=0x503000000040, lo=2, hi=8) at recur.c:9
#2  in sum_range (a=0x503000000040, lo=1, hi=8) at recur.c:9
#3  in sum_range (a=0x503000000040, lo=0, hi=8) at recur.c:9
#4  in main () at main.c:30

The CS107 GDB guide reads such a listing this way: “Each line represents a stack frame (ie. a function call)”. Frame 0 is the newest. Frames 1 to 3 are the same function, paused at line 9, the line with the recursive call: each is waiting for the frame below it to return so that it can add its own a[lo]. Nothing has been added yet. The additions happen on the way back up, newest frame first:

CS107, GDB Guide, the backtrace section. up and down move between frames; info frame prints one frame's addresses. In this build each sum_range frame is 64 bytes, so the eight live frames of the full call use half a kilobyte of the 8 MB stack. 
lo=8 returns 0
lo=7 returns 4  + 0   = 4
lo=6 returns 35 + 4   = 39
lo=5 returns 5  + 39  = 44
lo=4 returns 26 + 44  = 70
lo=3 returns 9  + 70  = 79
lo=2 returns 15 + 79  = 94
lo=1 returns 4  + 94  = 98
lo=0 returns 9  + 98  = 107

Work after the call runs on the way back up

Move the work to the other side of the recursive call and the order reverses. This function prints the range last to first:

void print_backwards(const int* a, size_t lo, size_t hi) {
    if (lo == hi) {
        return;
    }
    print_backwards(a, lo + 1, hi);   /* the rest first ... */
    printf(" %d", a[lo]);             /* ... then this one, on the way back up */
}

The frame for lo = 0 calls before it prints, and so does every frame under it. The deepest non-empty frame, lo = 7, is the first one to reach its printf, so 4 prints first, then 35, then 5, and 9 prints last: 4 35 5 26 9 15 4 9. Aspnes shows the same pair, printRangeRecursive with the print before the call and printRangeRecursiveReversed with it after. Remember this shape. Lesson 8's merge runs after both recursive calls, and lesson 12 frees a tree node after both of its children, for exactly this reason.

Aspnes, 5.3.1 Example of recursion in C: a block of routines that “print numbers i where start <= i < stop”, half-open like yours, in int rather than size_t.

Halve instead of shrinking by one

Shrinking by one puts one frame on the stack per element: eight frames for eight ints, a million for a million. Aspnes: “it's best to try to avoid linear recursions like the one in printRangeRecursive, where the depth of the recursion is proportional to the number of things we are doing. Much safer are even splits”. Halving gives a tree of calls instead of a chain, and the tree is only about log₂ n deep. The largest value of [0, 8) is the larger of the largest of [0, 4) and the largest of [4, 8):

Aspnes, 5.3.2.2 Blowing out the stack: “if we call printRangeRecursive(0, 1000000), we will probably get a segmentation fault after the first 100,000 numbers or so.” 
[0, 8)  9 4 15 9 26 5 35 4                    -> max(15, 35) = 35
[0, 4)  9 4 15 9      [4, 8)  26 5 35 4       -> max(9, 15) = 15,  max(26, 35) = 35
[0, 2)  9 4  [2, 4)  15 9  [4, 6)  26 5  [6, 8)  35 4
[0, 1) 9 [1, 2) 4 [2, 3) 15 [3, 4) 9 [4, 5) 26 [5, 6) 5 [6, 7) 35 [7, 8) 4    one element each
int max_range(const int* a, size_t lo, size_t hi) {
    if (hi - lo == 1) {
        return a[lo];                 /* one element is its own maximum */
    }
    size_t mid = lo + (hi - lo) / 2;
    int left = max_range(a, lo, mid);
    int right = max_range(a, mid, hi);
    return left > right ? left : right;
}

Three things to check against the two rules. The base case is one element, not zero, because the empty range has no maximum; the header says the range must hold at least one element. Both halves are strictly smaller than [lo, hi) whenever it holds two or more elements, because mid then lies strictly between lo and hi. And the deepest chain is [0, 8), [0, 4), [0, 2), [0, 1): four frames for eight elements, and only about twenty for a million. Lesson 8's merge sort is this function with a merge in place of the comparison.

Halve and keep one side

Binary search halves too, but it keeps only one half. Lesson 5 wrote it as a loop; here it is as a recursion on the sorted copy 4 4 5 9 9 15 26 35, searching for 26 and then for 7:

search 26 in [0, 8)   mid = 4, a[4] = 9,  26 > 9   keep [5, 8)
search 26 in [5, 8)   mid = 6, a[6] = 26  found     return &a[6]

search 7 in [0, 8)    mid = 4, a[4] = 9,  7 < 9    keep [0, 4)
search 7 in [0, 4)    mid = 2, a[2] = 5,  7 > 5    keep [3, 4)
search 7 in [3, 4)    mid = 3, a[3] = 9,  7 < 9    keep [3, 3)
search 7 in [3, 3)    empty                        return NULL
const int* search_range(const int* a, size_t lo, size_t hi, int target) {
    if (lo == hi) {
        return NULL;                  /* empty range: not here */
    }
    size_t mid = lo + (hi - lo) / 2;
    if (a[mid] == target) {
        return &a[mid];
    }
    if (target < a[mid]) {
        return search_range(a, lo, mid, target);      /* [lo, mid) */
    }
    return search_range(a, mid + 1, hi, target);      /* [mid + 1, hi) */
}

The half-open range earns its keep here. Dropping a[mid] from the left half is [lo, mid): no mid - 1, so nothing can wrap when mid is 0, the trap lesson 5 needed an explicit check for. Dropping it from the right half is [mid + 1, hi). Both halves exclude mid, so both are strictly smaller: rule 2 holds. Aspnes writes the same function with a length instead of two indices and the base case length == 0.

Aspnes, 5.3.3.1 Binary search: recursive and iterative versions. His recursive binarySearch(target, a, length) recurses on a with index for the bottom half and on a + index + 1 for the top half: pointer arithmetic where you pass lo and hi.

The interface

recur.h

#pragma once

#include <stddef.h>

/* Sum of the ints in a[lo..hi). Shrinks the range by one element per call. */
long sum_range(const int* a, size_t lo, size_t hi);

/* Print the ints in a[lo..hi) last to first, space-separated, no newline. */
void print_backwards(const int* a, size_t lo, size_t hi);

/* Largest int in a[lo..hi). The range must hold at least one element.
   Halves the range per call. */
int max_range(const int* a, size_t lo, size_t hi);

/* Binary search for target in the sorted range a[lo..hi).
   Returns a borrowed pointer to a matching element, or NULL if absent. */
const int* search_range(const int* a, size_t lo, size_t hi, int target);

Every function takes the array once and the range as two indices, the shape every recursive function in lessons 8 and 12 will keep. sum_range returns long so that the sum of many ints has room. The search returns a borrowed pointer, as lesson 5's did.

Reading the reports

1. A call that never shrinks. max_range(a, lo, hi) calls itself with the same range, forever. Each call pushes a frame until the 8 MB stack is gone:

AddressSanitizer:DEADLYSIGNAL
ERROR: AddressSanitizer: stack-overflow on address 0x7ffed9fb7ff8 ...
    #0 ... in max_range recur.c:25
    #1 ... in max_range recur.c:25
    #2 ... in max_range recur.c:25
    #3 ... in max_range recur.c:25
SUMMARY: AddressSanitizer: stack-overflow recur.c:25 in max_range

One function, one line number, all the way down. Aspnes calls this the “dead give-away”: “segmentation faults that produce huge piles of stack frames when you type where in gdb”. The line is the recursive call whose range did not shrink. When you see this column, find that line and ask what is smaller about its arguments. Here, nothing.

Aspnes, 5.3.2.3 Failure to make progress. where is gdb's other name for backtrace.

2. Print before the call. No report. The line reads backwards: 9 4 15 9 26 5 35 4, the array forwards, because every frame now prints before the frame under it gets a turn. The only difference between the two programs is which side of the call the work sits on.

3. A range that shrinks only sometimes. The search for 26 succeeds: [5, 8) is smaller than [0, 8) even with the wrong call, because mid happened to be 4. The search for 7 dies:

ERROR: AddressSanitizer: stack-overflow ...
    #0 ... in search_range recur.c:30
    #1 ... in search_range recur.c:41
    #2 ... in search_range recur.c:41
    #3 ... in search_range recur.c:41

Trace it: [2, 4) has mid = 3, and 7 < 9 keeps [2, 3). Then [2, 3) has mid = 2, 7 > 5, and the right half is [mid, hi) = [2, 3) again. Same column as report 1, with frame 0 at the base-case line because that is where the new frame is when the stack runs out. A range that shrinks on most inputs and not on one is still a broken rule 2; the test data has to include the input that finds it.

Also worth seeing once. Delete the base case of sum_range. gcc 13 warns at build time, infinite recursion detected [-Winfinite-recursion], and the run reports a heap-buffer-overflow, READ of size 4, 0 bytes after the 32-byte region, under nine sum_range frames. The calls did keep shrinking the range; they walked off the end of the block at a[8] long before the stack ran out. Missing base case, but the array was the first thing to give way.

Ask your teacher. If a recursive function you are writing has no line you can point to and say “this range is smaller”, stop and ask before running it. The same goes for a base case you cannot state in one sentence. Both questions are cheaper than reading a thousand-frame report.
