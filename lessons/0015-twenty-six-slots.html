Twenty-Six Slots

A trie is a tree whose every node holds twenty-six pointer slots, one per lowercase letter. Insert walks the slots and allocates through them; free visits all twenty-six before the node goes.

About 40 minutes Where: WSL, exercises/15-trie/ Mission · Cheat sheet · Lesson 14

The mission's required list ended with lesson 14. Stack, list, queue, tree, hashmap and graph are done, and CS107 asks for nothing more. This lesson is extra practice on two things you already own: the slot pattern from lessons 10 and 12, and the recursive post-order free from lesson 12. Skip it without guilt. Do it if you want those two patterns to sit deeper.

Your win today. Ship trie_t as an opaque ADT: insert through a struct node** slot chosen by subtraction, answer “whole word” and “prefix” with one shared finder and one flag test, and free seventeen nodes in post-order with a loop inside the recursion. Then read what UBSan, ASan and gcc say when the index, the flag and the free order go wrong.

A letter is a small number, so it can be an index

Take the letter 'c'. Your machine stores it as the number 99, and it stores 'a' as 97. Subtract: 99 - 97 = 2. So 'c' selects slot 2 of an array of 26, counting from 0. 'a' selects slot 0, 'b' slot 1, and 'z', which is 122, selects 122 - 97 = 25. In C that subtraction is written c - 'a', and it is ordinary integer arithmetic, because a char is an integer. Beej: “Deep down, char is just a small int”, and a character constant “will be converted to a char whose value is the same as the ASCII value”*. No table and no function call: the letter is the index.

'c'992third

'A'65-32256 bytes before the array

The last two rows are the trouble. 'A' gives -32 and '{' gives 26: one addresses memory before the array, the other addresses the slot one past its end. This trie accepts only 'a' to 'z', so every walk checks the letter before it indexes. Experiment 1 drops the subtraction and shows what an index of 97 does.

One node, twenty-six slots

Each node is one heap block holding 26 pointers and a flag. The trie struct holds the root and a count:

#define ALPHABET 26

struct node {
    struct node* child[ALPHABET];   /* slot i leads to the node for letter 'a' + i, or NULL */
    int is_end;                     /* 1 if a whole word ends at this node */
};

struct trie {
    struct node* root;              /* a live node even when the trie is empty */
    size_t count;                   /* whole words */
};

26 pointers of 8 bytes is 208 bytes. The int adds 4, and 4 bytes of padding bring the total to 216. The header says only typedef struct trie trie_t;; both structs live in trie.c, the opaque shape of lessons 9 to 12. struct node is spelled out as in lessons 11 and 12; lesson 10's typedef struct node node_t; names the same kind of private struct and is equally fine.

The test program prints node: 216 bytes from sizeof(struct node) through a one-line accessor, because main.c cannot take sizeof an opaque type. sizeof rounds a struct up to a multiple of its strictest member alignment, 8 here, so 212 becomes 216. The number 216 comes back in every sanitizer report below as the size of the region.

Insert "app", then "apple", into an empty trie. Give the blocks pretend addresses. Slot i of a node at address N lives at N + 8i, ordinary pointer arithmetic on the child array:

t ──▶ struct trie { root ──▶ 0x1000, count 2 }

0x1000  root           child[0]  ('a')  at 0x1000 ──▶ 0x2000
0x2000  after "a"      child[15] ('p')  at 0x2078 ──▶ 0x3000
0x3000  after "ap"     child[15] ('p')  at 0x3078 ──▶ 0x4000
0x4000  after "app"    is_end 1         child[11] ('l') at 0x4058 ──▶ 0x5000
0x5000  after "appl"   child[4]  ('e')  at 0x5020 ──▶ 0x6000
0x6000  after "apple"  is_end 1         all 26 slots NULL

Six blocks, 26 slots each, 156 slots in all, and five of them are not NULL. A word is not a node. A word is a path from the root, and the flag on the last node says whether that path is a whole word. "app" and "apple" share three nodes, and the node at 0x4000 is both the end of one word and the middle of the other. Doug Lloyd makes the same point in the CS50 short with bat inside batch*.

Ownership is lesson 12's, widened. The trie owns the root node, and every node owns the nodes its 26 slots address. NULL owns nothing. The six test words make 16 letter nodes plus the root: 17 nodes and one trie struct, 18 heap blocks, one trie_free.

Why calloc. new_node calls calloc(1, sizeof(struct node)), not malloc. cppreference: calloc “initializes all bytes in the allocated storage to zero”*. A zero pointer is NULL and a zero int is “not a word end”, which together are exactly the empty node. malloc would hand back 26 slots holding whatever the block held before, and the first walk would follow one of them as if it were a child. Lesson 3 used calloc for zeroed ints; here the zero is the structure's invariant. Swap in malloc and the sanitizer build dies on the first insert: UBSan reports member access within misaligned address 0xbebebebebebebebe for type 'struct node', because ASan fills fresh malloc bytes with 0xbe and the walk then follows that pattern as a pointer. Valgrind on the plain build says Conditional jump or move depends on uninitialised value(s) in trie_insert. Not one of the three experiments below, but worth one look if you have time.

Insert: walk the slots, allocate through them

Inserting "apple" after "app" is the walk in the diagram: three slots already lead somewhere, two hold NULL. For every letter the code takes the address of the slot, and when the slot holds NULL it writes a new node through it. That is lesson 10's node_t** link and lesson 12's insert_at(struct node** slot, ...), with the branch chosen by subtraction instead of a comparison:

int trie_insert(trie_t* t, const char* word) {
    struct node* cur = t->root;
    for (const char* p = word; *p != '\0'; p++) {
        int i = slot_index(*p);                  /* c - 'a', or -1 outside 'a'..'z' */
        if (i < 0) {
            return -1;
        }
        struct node** slot = &cur->child[i];     /* the address of the pointer to change */
        if (*slot == NULL) {
            *slot = new_node();                  /* write through the slot */
            if (*slot == NULL) {
                return -1;
            }
        }
        cur = *slot;
    }
    if (cur->is_end) {
        return 0;                                /* already a whole word: nothing changed */
    }
    cur->is_end = 1;
    t->count++;
    return 1;
}
*p    i    slot                     *slot before   action
'a'   0    &root->child[0]          0x2000         follow
'p'   15   &(0x2000)->child[15]     0x3000         follow
'p'   15   &(0x3000)->child[15]     0x4000         follow
'l'   11   &(0x4000)->child[11]     NULL           calloc 0x5000, write it into the slot
'e'   4    &(0x5000)->child[4]      NULL           calloc 0x6000, write it into the slot
'\0'       stop: cur is 0x6000, is_end 0, so set it, count becomes 2, return 1

The loop stops at the string's terminator. Beej: a C string is “a pointer to the first character” plus “a zero-valued byte (or NUL character) somewhere in memory after the pointer that indicates the end of the string”*. No strlen, no strcmp: the trie reads one char at a time and needs nothing from <string.h> at all. The static helper slot_index holds the range check from the table and returns c - 'a', or -1.

Three return values, one honest contract. 1 means inserted. 0 means the word was already there: a duplicate, nothing changed, as in lesson 12. -1 means a letter outside 'a'..'z' or a failed calloc. On -1 no word is counted, but the nodes created for the letters before the bad one stay in the trie. They are owned like every other node and trie_free releases them, so nothing leaks; the header says exactly that instead of promising “unchanged”. If “unchanged” matters to a caller, run a validating loop over the word before the inserting one. The exercise leaves that choice to you.

One finder, two questions

trie_contains and trie_starts_with walk the same path and differ only in the last test. So one static helper does the walk and returns the node it reaches, or NULL if the path ends early:

static const struct node* find_node(const struct node* root, const char* s) {
    const struct node* cur = root;
    for (const char* p = s; *p != '\0' && cur != NULL; p++) {
        int i = slot_index(*p);
        if (i < 0) {
            return NULL;
        }
        cur = cur->child[i];
    }
    return cur;                                  /* the node at the end of s, or NULL */
}

int trie_contains(const trie_t* t, const char* word) {
    const struct node* n = find_node(t->root, word);
    return n != NULL && n->is_end;             /* is_end is read only when n is live */
}

int trie_starts_with(const trie_t* t, const char* prefix) {
    return find_node(t->root, prefix) != NULL;
}

Three lookups on the diagram above. "ap": 'a' leads to 0x2000, 'p' to 0x3000, the string ends, and find_node returns 0x3000. Its is_end is 0, so contains says 0 and starts_with says 1. "cat": root->child[2] is NULL, so cur becomes NULL, the loop condition fails, and both say 0. "": the loop never runs and find_node returns the root, so starts_with("") is 1 for every trie, and contains("") is 1 only if the empty word was inserted, which this test never does.

The cost of any lookup is the length of the string, not the number of words stored. algs4's TrieST states it for its 256-way version: put, contains and delete “take time proportional to the length of the key (in the worst case)”*. Six words or six million, "apple" is five steps from the root.

Free: twenty-six children, then the node

static void free_nodes(struct node* n) {
    if (n == NULL) {
        return;
    }
    for (int i = 0; i < ALPHABET; i++) {
        free_nodes(n->child[i]);
    }
    free(n);                                     /* last: every slot has been read */
}

This is lesson 12's post-order free with a loop where the BST had two calls, and the rule is the same: the slots live inside the node's block, so the node is freed only after all 26 have been read. Free it first and the loop reads child[0] out of a dead block. Experiment 3 does that, and gcc 13 sees it coming.

Count the calls. Every node makes 26, so 17 nodes make 442. Of those, 425 meet NULL and return at once; 17 do the work. That is the price of a slot for every letter, used or not. Now count the frames. The recursion goes one frame deeper per letter, so the deepest point of this run is inside "bandana": the root frame plus seven, eight frames, each holding its n and its i. In lesson 12 the depth was the tree's height and depended on insertion order. Here it is the length of the longest word and nothing else.

The six words hold 30 letters between them. The trie stores them in 16 letter nodes, because shared prefixes share nodes, plus the root: 17 nodes at 216 bytes is 3,672 bytes, and of the 442 slots, 16 are in use. algs4's TrieST widens the array to R = 256 (“extended ASCII”) and every node still carries all 256 references*. Doug Lloyd closes the CS50 short on that trade: near-constant-time insert and lookup, paid for with “a lot of space and memory”*. That is why the trie is optional here: the pointer work is lessons 10 and 12 again, and the structure itself is a memory trade worth knowing the price of.

trie_free calls free_nodes(t->root) and then free(t). 17 node frees and one struct free is 18. valgrind will report 19 and 19; the nineteenth is printf's buffer.

The interface

trie.h

#pragma once

#include <stddef.h>

typedef struct trie trie_t;

/* Create an empty trie (one root node) on the heap. Returns NULL on allocation failure. */
trie_t* trie_new(void);

/* Free every node, children before parent, then the trie. Consumes ownership.
   trie_free(NULL) does nothing. */
void trie_free(trie_t* t);

/* Insert word, lowercase 'a' to 'z' only. Returns 1 if inserted, 0 if word was already
   present, -1 on a character outside 'a'..'z' or on allocation failure. On -1 no word is
   counted, but nodes for a prefix of word may remain; the trie owns them and trie_free
   releases them. */
int trie_insert(trie_t* t, const char* word);

/* Return 1 if word was inserted as a whole word, else 0. */
int trie_contains(const trie_t* t, const char* word);

/* Return 1 if the trie holds the path spelled by prefix, else 0. Every inserted word
   leaves its prefixes as paths, and "" is the root, so "" always answers 1. */
int trie_starts_with(const trie_t* t, const char* prefix);

/* Return the number of whole words in the trie. */
size_t trie_count(const trie_t* t);

/* Size in bytes of one private node, for the test program to report. */
size_t trie_node_size(void);

Two functions take trie_t* because they change the trie. Three take const trie_t* because they only read, and find_node behind them takes const struct node* for the same reason. No pointer into a node ever crosses the header: every answer is an int or a size_t, so no caller can hold a node after trie_free.

Reading the three reports

Experiment 1, index 97. The first word is "apple" and its first letter is 'a', 97. The build has -fsanitize=undefined as well as address, and child is declared with 26 elements, so the undefined-behaviour sanitizer speaks first, before any memory is touched (paths and line numbers trimmed):

trie.c:67:41: runtime error: index 97 out of bounds for type 'node *[26]'
=================================================================
ERROR: AddressSanitizer: heap-buffer-overflow on address 0x511000000348
READ of size 8 at 0x511000000348 thread T0
    #0 in trie_insert trie.c:68
    #1 in main main.c:24
0x511000000348 is located 560 bytes after 216-byte region [0x511000000040,0x511000000118)
allocated by thread T0 here:
    #0 in calloc
    #1 in new_node trie.c:25
    #2 in trie_new trie.c:33
    #3 in main main.c:17

Do the arithmetic the report did. Slot 97 lives at offset 97 × 8 = 776 from the node's start. The node is 216 bytes, and 776 - 216 = 560: the read landed 560 bytes past the end of the block. The block was allocated by new_node under trie_new, so it is the root, and the first letter of the first word already missed the array. Under the plain build the same read returns whatever sits 560 bytes past the root and the walk follows it; nothing reports anything until the program crashes somewhere else.

Experiment 2, path is not word. Nothing crashes and nothing leaks. The output is the only evidence, and one line is wrong:

contains "app": yes
contains "ap": yes
contains "apple": yes
...
==12345== total heap usage: 19 allocs, 19 frees, 7,784 bytes allocated
==12345== ERROR SUMMARY: 0 errors from 0 contexts

The path a, p exists because "app" and "apple" pass through it. Reading a live node's is_end, or not reading it, is legal C either way, so no sanitizer has anything to say. The expected-output check is the only tool that catches a wrong answer, which is why every lesson ships one.

Experiment 3, parent before children. gcc 13 warns at build time. Note the wording: “may be”, not “is”, because the read sits inside a loop and the compiler is less sure than it was in lesson 12:

   48 |         free_nodes(n->child[i]);
      |         ^~~~~~~~~~~~~~~~~~~~~~~
trie.c:46:5: note: call to ‘free’ here
   46 |     free(n);

Run it anyway and the thirteen lines print, because the bug is in trie_free, and then:

    #0 in free_nodes trie.c:48

    #2 in main main.c:45

    #1 in free_nodes trie.c:46

“0 bytes inside” is child[0], the first slot the loop reads. Only one free_nodes frame sits in the “freed by” column: the root was freed on the very first call, before any recursion happened, and the loop then read its first slot out of the dead block. In lesson 12 the same mistake read left at offset 8; here the first read is at offset 0 because the slots come first in the struct.

Read next

Everything here is C-based teaching or has no code at all. Read in this order; the first item is a video, because no C source file for a trie exists in the sources this course uses.

  1. Watch first: the structure, hand-traced in C terms. CS50 Shorts, Doug Lloyd, Tries; the CS50x page for the short carries a transcript. He builds a ten-way trie keyed by the digits of a year, so every node holds ten pointers instead of your twenty-six, and he names the 26-way version as the dictionary case. Watch for three moments. When a path is null he says “I have to malloc a new node, have 1 point there”: that is your *slot = new_node(), with the slot chosen by a digit instead of c - 'a'. He keeps a global root that is set once and “never touched again”; your root lives inside the opaque struct, set once by trie_new. And he ends on the trade, near-constant-time insert and lookup for “a lot of space and memory”, which is the sidenote's 3,672 bytes for 30 letters. No code listing and no free; every node he mallocs is yours to free in post-order.

  2. The first-course version, in two pictures. CS50x notes, Week 5, Tries. Four sentences and two drawings of a 26-way trie holding Toad and then Tom. Their “26 × 4 = 104 nodes just to store Toad” is counting slots: four nodes of 26 slots each, and your test program's 17 nodes hold 442 of them. Their “search time of O(1)” means what the lookup paragraph above means: the cost is the length of the key, and does not grow with the number of words stored.

  3. The two type facts the walk depends on. Beej, 14.2 Character Types: “Deep down, char is just a small int”, and “char is actually a number, so can we do math on it? Yup!” That is the whole justification for c - 'a'. Then 7.6 String Termination, for the '\0' every walk in trie.c stops on, and for why no <string.h> call was needed: the terminator is the length.

  4. The one library rule behind new_node. cppreference, calloc, first sentence: it “initializes all bytes in the allocated storage to zero”. Twenty-six NULL slots and a clear flag, for the price of one word changed from malloc.
