Lesson 10 · DSA in C

Smaller Left, Larger Right

A binary search tree is a linked list that forks. Every function on it is a short recursive helper that holds one node pointer per stack frame, and the tree's height is the depth of your C stack.

About 45 minutes Where: WSL, exercises/10-bst/ Mission · Cheat sheet · Lesson 9
Your win today. Ship bst_t as an opaque ADT with eight public functions, every one a thin wrapper over a private recursive helper. Insert through a slot, free in post-order, and read an AddressSanitizer use-after-free timeline that shows the recursion itself.

Setup · paste once · not something to learn

Put this Makefile in the exercise folder. The ⇥ marks must be real tabs.

CC     = gcc
CFLAGS = -std=gnu11 -Wall -Wextra -g
SAN    = -fsanitize=address,undefined
SRC    = main.c bst.c

bst: $(SRC) bst.h
⇥$(CC) $(CFLAGS) $(SAN) -o bst $(SRC)

bst-plain: $(SRC) bst.h
⇥$(CC) $(CFLAGS) -o bst-plain $(SRC)

.PHONY: check clean

⇥valgrind --leak-check=full --error-exitcode=1 ./bst-plain
clean:
⇥rm -f bst bst-plain

A node is one key and two slots

Insert the keys 50 30 70 20 40 60 80 in that order into an empty tree. Each key goes into a fresh heap block. Each block holds the key and two pointers, and every pointer either addresses another block or is NULL:

main's stack        heap
t ──────────▶ struct bst { root ──▶ 0x100, count 7 }

0x100  [ 50 | left 0x140 | right 0x180 ]
0x140  [ 30 | left 0x1c0 | right 0x200 ]     0x180  [ 70 | left 0x240 | right 0x280 ]
0x1c0  [ 20 | NULL | NULL ]  0x200  [ 40 | NULL | NULL ]  0x240  [ 60 | NULL | NULL ]  0x280  [ 80 | NULL | NULL ]

Read any node and look left: every key down there is smaller. Look right: every key down there is larger. Sedgewick and Wayne state the rule as “the key in any node is larger than the keys in all nodes in that node's left subtree and smaller than the keys in all nodes in that node's right subtree”*. That is the invariant. Every function below either relies on it or preserves it.

In C the node is a private struct in bst.c, and so is the tree that holds the root and a count. The header only says typedef struct bst bst_t;, exactly as the stack, list and queue did. As in lesson 9, struct node is spelled out; lesson 8's node_t typedef names the same kind of private struct and is equally fine:

struct node {
    int key;
    struct node* left;
    struct node* right;
};

struct bst {
    struct node* root;
    size_t count;
};
One node is 24 bytes on your machine: 4 for the int, 4 of padding so the first pointer sits on an 8-byte boundary, then 8 and 8. The number 24 shows up in the sanitizer reports later; that is where it comes from.

Ownership is the same as lesson 8's list, forked: the tree owns the root node, and every node owns the two nodes its pointers address. A NULL pointer owns nothing. Seven nodes, seven owners, one bst_free.

Recursion walks the heap using the stack

The list in lessons 8 and 9 had one “next” per node, so a while loop walked it. A tree has two, and the natural walk is recursion: a function that handles one node and calls itself on a child. Search for 60 in the tree above:

contains_in(0x100, 60)        60 > 50: go right
  contains_in(0x180, 60)      60 < 70: go left
    contains_in(0x240, 60)    60 == 60: return 1

Three calls, three stack frames, each holding exactly one node pointer. The tree has height 2 (two links from the root down to 60), so at most height + 1 frames are alive at once. Nothing on the heap changes; the stack grows and shrinks. In C:

static int contains_in(const struct node* n, int key) {
    if (n == NULL) {
        return 0;                          /* fell off the tree: absent */
    }
    if (key < n->key) {
        return contains_in(n->left, key);
    }
    if (key > n->key) {
        return contains_in(n->right, key);
    }
    return 1;
}

int bst_contains(const bst_t* t, int key) {
    return contains_in(t->root, key);      /* the public wrapper is one line */
}

Two things to copy for every helper in this lesson. First, the base case comes first: a NULL node is a tree with nothing in it, and the function answers for it without touching memory. Second, the public function is a wrapper that unpacks t->root and calls the helper; the helper is static and takes a struct node*, a type the header never mentions.

Frames per call cost stack space. With the keys inserted in sorted order every node hangs right and the height is n - 1. I built that chain with 50,000 keys and the default 8 MB stack still held; with the stack cut to 1 MB, 40,000 sorted inserts died with AddressSanitizer: stack-overflow inside a column of insert_at frames. Sedgewick and Wayne: running times “depend on the shapes of the trees, which, in turn, depends on the order in which keys are inserted”*. Balancing is CS166 material, not ours. Know the failure mode, then move on.

Insert: pass the slot, not the node

Insert 40 into the tree as it stood after 50 30 70 20. The walk goes right of nothing, left of 50, right of 30, and arrives at a NULL. The new node has to be written into that pointer, which is the right member of node 30, at address 0x150 inside the 0x140 block:

insert_at(&t->root, 40)          *slot is 0x100 (50).  40 < 50: recurse on &(0x100)->left
  insert_at(&(0x100)->left, 40)  *slot is 0x140 (30).  40 > 30: recurse on &(0x140)->right
    insert_at(0x150, 40)         *slot is NULL:  *slot = new node 0x200

0x140  [ 30 | left 0x1c0 | right NULL ]  ──▶  [ 30 | left 0x1c0 | right 0x200 ]
                          ^ 0x150, the slot

This is lesson 8's slot pattern with one more branch: the helper receives the address of the pointer to change, a struct node**. At the root that address is &t->root; one level down it is &n->left or &n->right. The base case is a slot that holds NULL, and the write goes through the slot:

static int insert_at(struct node** slot, int key) {
    if (*slot == NULL) {
        *slot = new_node(key);             /* writes into the parent, or into t->root */
        return *slot != NULL;
    }
    struct node* n = *slot;
    if (key < n->key) {
        return insert_at(&n->left, key);
    }
    if (key > n->key) {
        return insert_at(&n->right, key);
    }
    return 0;                              /* duplicate: tree unchanged */
}
Sedgewick and Wayne write insert the other way round: the helper returns the node and every caller reassigns, node.left = put(node.left, ...)*. Both are correct. The slot form writes only the one pointer that changes, and it is the form you already own from lesson 8.

If the helper took a struct node* n instead and did n = new_node(key), it would write into its own parameter, a copy that dies with the frame. The parent's NULL would stay NULL, the node would be unreachable, and the count would still go up. You will make that change on purpose in the experiments.

Why bst_insert returns 1 or 0. This tree is a set: a key is in it once or not at all, so a duplicate is not an error, it is simply “nothing to do”. A failed malloc is also “nothing changed”. Both cases return 0 and leave the tree exactly as it was, and the caller adds the return value to its own count of successful inserts. A caller that needs to tell the two apart can call bst_contains first. A three-valued return would be the alternative; not worth it here.

Min, height, in-order: three helpers, three shapes

Min is the leftmost node. Start at the root and follow left until it is NULL; the node you stand on holds the smallest key. Sedgewick and Wayne: “if the left link is not null, the smallest key in the BST is the smallest key in the subtree rooted at the node referenced by the left link”*. The helper takes a node that is not NULL; the wrapper checks for the empty tree and returns NULL for it.

bst_min returns const int*: the address of the key member inside the leftmost node. That pointer is borrowed, like lesson 4's words_longest. The node owns the int. The pointer is valid until that node is freed, which happens in bst_free. The caller never frees it and never keeps it across bst_free. The contract goes in the header in those words.

Height is 1 + the taller child. For the tree above: node 20 has two NULL children, so its height is 1 + max(-1, -1) = 0. Node 30 has two children of height 0, so 1 + 0 = 1. The root has children of height 1 and 1, so 2. The convention, taken from the algs4 reference code, is that the empty tree has height -1 and a single node has height 0*. Some books count nodes instead, so an empty tree is 0 and a leaf is 1. Either is fine; the header states which one, and the expected output holds you to it.

static int height_of(const struct node* n) {
    if (n == NULL) {
        return -1;
    }
    int l = height_of(n->left);
    int r = height_of(n->right);
    return 1 + (l > r ? l : r);
}

In-order prints sorted. Print everything left of the node, then the node, then everything right of it. By the invariant, everything left is smaller and everything right is larger, so the keys come out ascending*. The helper is three lines after the base case. Print each key with one leading space and let the wrapper add the newline, so the caller can print a label first.

Free: children before the node

Freeing is a walk too, and the order matters. A node's left and right live inside the node's block. Once that block is freed, reading either of them is a read of freed memory. cppreference: “The behavior is undefined if after free() returns, an access is made through the pointer ptr”*. So the two children go first, then the node. That order is called post-order:

static void free_nodes(struct node* n) {
    if (n == NULL) {
        return;
    }
    free_nodes(n->left);
    free_nodes(n->right);
    free(n);                               /* last: nothing reads n after this */
}

bst_free calls this on the root, then frees the struct bst itself. Seven node blocks and one tree block: eight frees for eight allocations. valgrind will report nine of each; the ninth is the buffer printf allocates behind your back, and it is freed at exit.

The interface

bst.h

#pragma once

#include <stddef.h>

typedef struct bst bst_t;

/* Create an empty tree on the heap. Returns NULL on allocation failure. */
bst_t* bst_new(void);

/* Free every node, then the tree. Consumes ownership. bst_free(NULL) does nothing. */
void bst_free(bst_t* t);

/* Insert key. Returns 1 if inserted, 0 if key was already present or allocation failed.
   On 0 the tree is unchanged. */
int bst_insert(bst_t* t, int key);

/* Return 1 if key is in the tree, else 0. */
int bst_contains(const bst_t* t, int key);

/* Return a borrowed pointer to the smallest key, or NULL if the tree is empty.
   The pointer is owned by the tree and dies with bst_free. */
const int* bst_min(const bst_t* t);

/* Return the height: -1 for an empty tree, 0 for a single node. */
int bst_height(const bst_t* t);

/* Print every key in ascending order, each preceded by one space, then a newline. */
void bst_print_inorder(const bst_t* t);

/* Return the number of keys in the tree. */
size_t bst_count(const bst_t* t);

Two functions take bst_t* because they change the tree. Five take const bst_t* because they only read it. The helpers behind the readers take const struct node* for the same reason.

  6. Break it three ways, one at a time.

Reading the use-after-free timeline

Experiment 3 is the one to read slowly. The plain build printed min again: 20, because nothing had reused those 24 bytes yet. That is what a dangling pointer does most of the time: it works, until it does not. The sanitizer build tells the whole story in three stack traces (paths and line numbers trimmed):

ERROR: AddressSanitizer: heap-use-after-free on address 0x5030000000d0
READ of size 4 at 0x5030000000d0 thread T0
    #0 in main main.c:37                      ← the printf of *m

0x5030000000d0 is located 0 bytes inside of 24-byte region
freed by thread T0 here:
    #0 in free
    #1 in free_nodes bst.c:91
    #2 in free_nodes bst.c:89
    #3 in free_nodes bst.c:89
    #4 in bst_free bst.c:110
    #5 in main main.c:36

previously allocated by thread T0 here:
    #0 in malloc
    #1 in new_node bst.c:20
    #2 in insert_at bst.c:33
    #3 in insert_at bst.c:38
    #4 in insert_at bst.c:38
    #5 in bst_insert bst.c:115
    #6 in main main.c:17

Read it bottom up. The block was allocated by new_node under three insert_at frames: root, then left of 50, then left of 30. That is the path to key 20, two links deep, three frames. It was freed under three free_nodes frames: the same path, walked by post-order. Then main read 4 bytes at offset 0, the key member, after the node's lifetime ended. The recursion you wrote is visible in both timelines; count the frames and you can name the node.

Experiment 1 gives the same error type from inside bst.c, with one different number:

bst.c: In function ‘free_nodes’:
warning: pointer ‘n’ used after ‘free’ [-Wuse-after-free]
...
ERROR: AddressSanitizer: heap-use-after-free
READ of size 8 at 0x503000000048 thread T0
    #0 in free_nodes bst.c:90
    #1 in bst_free bst.c:110
0x503000000048 is located 8 bytes inside of 24-byte region

Eight bytes in, size 8: that is the left pointer, read by free_nodes(n->left) after free(n). The compiler saw it too, because the free and the read are in the same function. It cannot see experiment 3, where the free is two files away.

Experiment 2 never crashes. It prints wrong answers, then valgrind names the loss:

inserted: 8 of 8
inorder:
count: 8
min: none
height: -1
...
==12345== 192 bytes in 8 blocks are definitely lost in loss record 1 of 1
==12345==    by 0x...: new_node (bst.c:20)
==12345==    by 0x...: insert_at (bst.c:33)
==12345==    by 0x...: bst_insert (bst.c:114)
==12345==    by 0x...: main (main.c:17)

Eight blocks, not seven: with the root still NULL, every insert took the base case, so the duplicate 30 was never seen. Eight times 24 bytes is 192. The tree is empty, the count says 8, and the nodes are unreachable. When a “returns 1” insert leaves the structure empty, the write went into a copy.
