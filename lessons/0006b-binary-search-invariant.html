Say Where It Must Be

Common sense cannot check a binary search. One sentence can. Write the sentence, check three things against it, then let the machine try every small case.

About 35 minutes Where: WSL, exercises/06-recursion/ Mission · Cheat sheet · Lesson 6
Your win today. State the invariant of search_range in one sentence, use it to find the two bugs in your own draft, rewrite the function so that every line obeys the sentence, and add a check that compares it with a linear scan over 306 cases.

You are in good company

You said it feels impossible to be sure a binary search is right by common sense. That is not a gap in you. It is the most documented fact about this function. Jon Bentley gave the problem to professional programmers with two hours and any language they liked. His count: “90 percent of the programmers found bugs in their code”. Knuth, on the same function: “the details can be surprisingly tricky”. And the program Bentley proved correct in that column carried an overflow bug for twenty years, until Joshua Bloch found it in 2006.

Bentley, Programming pearls: Writing correct programs, CACM, December 1983 (PDF). Also: “while the first binary search was published in 1946, the first published binary search without bugs did not appear until 1962.” Quoted in Wikipedia, Binary search, Implementation issues, which adds that most of Bentley's programmers “made an error in defining the exit conditions”. Bloch, Nearly All Binary Searches and Mergesorts are Broken (2006). The bug is (low + high) / 2; the fix is the lo + (hi - lo) / 2 you already use.

Bentley's cure was not more care. It was a sentence he could check the code against. Lesson 6 gave you two rules and an act of trust. Those prove the calls stop. They say nothing about whether the answer is right. For that you need one more thing.

The sentence

Binary search never knows where the target is. It only ever knows where the target must be if it is anywhere. Bentley wrote that as MustBe(range): “if T is anywhere in the array, then it must be in range”. For your function the range is [lo, hi), so the sentence is:

Bentley 1983, “Writing The Program”. His loop keeps MustBe(range) as a loop invariant; your recursion keeps it as a promise on every call. The CMU notes write the same promise as contract comments in C syntax.
The promise. On every call to search_range(a, lo, hi, target): a[0..n) is sorted, and if target is anywhere in a[0..n), then it is in a[lo..hi).
Pfenning, 15-122 Lecture 6: Binary Search (CMU, 2017). Their code says //@requires is_sorted(A, 0, n); and keeps 0 <= lo && lo <= hi && hi <= n as a loop invariant. This is the glossary's invariant.

Write it above the function before you write the function. Then every line has a judge:

/* Promise on every call: a[0..n) is sorted, and if target is anywhere
   in it, then target is in a[lo..hi). */
const int* search_range(const int* a, size_t lo, size_t hi, int target) {
    if (lo == hi) {
        return NULL;                  /* empty range + promise: nowhere */
    }
    size_t mid = lo + (hi - lo) / 2;  /* lo <= mid < hi */
    if (a[mid] == target) {
        return &a[mid];
    }
    if (target < a[mid]) {
        return search_range(a, lo, mid, target);      /* [lo, mid) */
    }
    return search_range(a, mid + 1, hi, target);      /* [mid + 1, hi) */
}

Three checks

Bentley argues a loop in three parts: initialization, preservation, termination. For a recursive function the same three parts read like this.

Bentley 1983: “Initialization. The loop invariant is true when execution of the loop begins. Preservation. If the invariant holds at the beginning of an iteration and the loop body is executed again, then the invariant will still be true. Termination. Upon termination of the loop, the desired result will hold.” Cornell's CS 2112 notes state the same three obligations for Java.
CheckQuestionFor search_range
1. First callDoes the caller keep the promise?main passes [0, n). Everything is inside it. Kept.
2. Every callDoes each recursive call keep the promise?Two calls to check, below.
3. Every returnGiven the promise, is each return right?Two returns to check, below.

Check 2, the left call. We are in the branch target < a[mid]. The array is sorted, so every index i >= mid has a[i] >= a[mid] > target. The target is at none of them. If it is anywhere, it is in [lo, mid). The promise is kept. Note that a[mid] itself is dropped, and dropping it needs no subtraction: half-open ranges exclude their right end for free.

Check 2, the right call. Now target > a[mid] (equality already returned). Sorted, so every i <= mid has a[i] <= a[mid] < target. If anywhere, it is in [mid + 1, hi). Kept. Both arguments used the word sorted. Take that word away and neither line follows; that is what the precondition in the header is for.

Check 3, the empty return. lo == hi means the range holds nothing. The promise says: if the target is anywhere, it is in this empty range. So it is nowhere. NULL is the right answer, not a guess.

Check 3, the found return. a[mid] == target, and &a[mid] points at it. Right by inspection. The header promises a matching element, not the first one, so with duplicates any match is correct.

Three checks, four short arguments, and no trace of any particular input. That is the whole proof. Lesson 6's shrink rule supplies the last piece: the calls stop.

Why the halves are always smaller

Your other worry was the split. Does “halve” really give two strictly smaller ranges every time, including at size one and size two? This is arithmetic, not intuition. Call the size k = hi - lo, and we are past the base case, so k >= 1. Then mid = lo + k / 2 with integer division:

k / 2 >= 0          so   mid >= lo
k / 2 <  k          so   mid <  hi      (true for every k >= 1)
therefore           lo <= mid < hi

From mid < hi <= n, reading a[mid] is in bounds. From lo <= mid, the left half [lo, mid) has k / 2 elements, fewer than k. From mid < hi, the right half [mid + 1, hi) has k - k / 2 - 1 elements, also fewer than k. The CMU notes put exactly this fact into the code as //@assert lo <= mid && mid < hi;. The small sizes, the ones that worry you, look like this:

Pfenning, Lecture 6, section 4 Termination: “the intervals from lo to mid and from mid+1 to hi are both strictly smaller than the original interval.” You can write the same line in C with assert(lo <= mid && mid < hi); from <assert.h>.

Your draft, checked

This is the search_range in your recur.c today, under a header that promises the half-open range a[low..high):

if (low > high) {
    return NULL;
}
int mid = (low + high) / 2;
if (a[mid] == target) {
    return &a[mid];
}
if (target > a[mid]) {
    return search_range(a, mid+1, high, target);
}
return search_range(a, low, mid-1, target);

Check 3 fails at the base case. For a half-open range, empty means low == high. The test low > high lets [3, 3) through as if it held something. The code then reads a[3], which is not in the range, and calls itself with [3, 3) again. That is lesson 6's report 3: a stack overflow, one column of the same line.

Check 2 fails at the left call. [low, mid - 1] is closed-range arithmetic. The half-open left half is [low, mid), with no subtraction at all. Under size_t, mid - 1 at mid == 0 wraps to the largest value, and your int mid then turns that into -1. That is the report you got when I ran it: stack-buffer-underflow at recur.c:44, a read of 4 bytes just before the array.

The precondition fails in main. {5, 2, 3, 4, 0} is not sorted. Both halves of check 2 used the word sorted. On this input the function keeps no promise, so no result it gives means anything, right or wrong. A test that breaks the precondition tests nothing.

None of this says the closed form is wrong. Lesson 5's [low, high] has its own sentence, “if anywhere, then in [low, high]”, and passes the same three checks, at the price of two guards under size_t. The mistake is mixing: a half-open header over a closed body. Pick one convention, write it in the header, and make every line obey it.

Learning record 0006 (2026-09-13): your closed search needed explicit n == 0 and mid == 0 checks before n - 1 and mid - 1. The half-open form needs neither, which is why lessons 6 to 12 use it.

Let the machine bombard it

A proof on paper can still miss a slip in the typing, as Bentley's overflow shows. His answer was to test every small size exhaustively: “Testing N from 0 to 10 covers the empty array, common sizes for bugs (one, two and three), several powers of two, and many numbers one away from a power of two … it used an insignificant amount of computer time”. You have a slow function that is obviously right, the linear scan. Make the fast one agree with it on every prefix of the sorted array and every target from 3 to 36:

Bentley 1983, the testing paragraph before “Principles of Program Verification”: “I let a computer do what it's good at and bombard the program with test cases.” 
/* Slow and obviously right: is target anywhere in a[0..n)? */
static int linear_has(const int* a, size_t n, int target) { ... }

/* Every prefix length of the sorted array, every target from 3 to 36:
   the search must agree with the linear scan. Returns the failure count. */
static int check_search(const int* sorted, size_t n, int* cases) {
    int failures = 0;
    *cases = 0;
    for (size_t len = 0; len <= n; len++) {
        for (int t = 3; t <= 36; t++) {
            const int* p = search_range(sorted, 0, len, t);
            int expect = linear_has(sorted, len, t);
            (*cases)++;
            if ((p != NULL) != expect || (p != NULL && *p != t)) {
                printf("FAIL: n = %zu, target %d, %s\n", len, t,
                       p == NULL ? "not found" : "wrong element");
                failures++;
            }
        }
    }
    return failures;
}

Nine sizes, 0 to 8, cover empty, one, two, three, the powers of two and their neighbours. Thirty-four targets cover below the first element, every present value, every gap, the duplicates and above the last: 306 cases. The check compares the outcome and the value found, never the index, because the header promises a matching element and 4 4 has two. Hand tests reach a handful of ranges. This reaches every one that eight elements can produce.

Read next

Everything here is C, C-like with contracts, or language-free. Read in this order.

  1. The same function, with its contracts written in the code. Frank Pfenning, 15-122 Lecture 6: Binary Search (CMU, 2017, PDF). Their invariant says what has been ruled out (A[lo - 1] < x and A[hi] > x) where yours says what remains; check that the two are the same promise.

  2. The classic. Jon Bentley, Programming pearls: Writing correct programs (CACM, 1983, PDF, six pages). Read from “The Challenge of Binary Search” to “Principles of Program Verification”. His code is closed-range pseudocode with 1-based indices; follow the argument, not the indices.
