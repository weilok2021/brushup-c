Lesson 9 · Dynamic-array stack · DSA in C

Grow on Push

A stack of ints in a heap block that doubles when it fills. The client holds one pointer and never sees inside. This is the first abstract data type of the course, and lessons 10, 11 and 12 copy its shape.

About 40 minutes Where: WSL, exercises/09-stack/ Mission · Cheat sheet · Lesson 8
Your win today. Ship a stack as a module: a header that hides the struct, a .c that owns two heap blocks, a push that grows through a temporary pointer and survives allocation failure, and a test program that proves the LIFO order and the empty case.

Setup · paste once · not something to learn

Three places, two owners

Push 10, 20 and 30 onto a stack whose block holds four ints. Here is every byte, and where it lives:

main's frame          heap block A (24 bytes)        heap block B (16 bytes)
+-------------+       +----------------------+       +----+----+----+----+
| s   0x5030  |-----> | items     0x5020     |-----> | 10 | 20 | 30 | ?? |
+-------------+       | count     3          |       +----+----+----+----+
  8 bytes             | capacity  4          |         [0]  [1]  [2]  [3]
                      +----------------------+
                        struct stack                   capacity ints, count in use

Three places. The handle s is a pointer in main's frame; it dies when main returns. Block A is the struct: one pointer and two counts, 8 + 8 + 8 = 24 bytes on the heap. Block B is the items: capacity ints, of which the first count are in use. The top of the stack is items[count - 1], here 30. Slot 3 holds garbage and is never read.

Two owners. The struct owns block B: it holds the only pointer to it, and it must free it. The caller owns the struct, through s, and must hand it back with stack_free. That is the two-level ownership from lesson 4 (char** array owning its strings), with a struct in place of the outer array.

Invariants to keep in every function: count <= capacity, items points at a live block of capacity ints, and items[0..count) holds the values from bottom to top. An invariant is a fact that is true between calls; each function may break it briefly inside, but must restore it before returning.

The client sees a name, not a shape

The header declares the type without its members:

typedef struct stack stack_t;       /* in stack.h: a name only */

The members appear once, in stack.c:

struct stack {                      /* in stack.c: the shape */
    int* items;
    size_t count;
    size_t capacity;
};

To main.c, struct stack is an incomplete type: a type whose size the compiler does not know. C lets you declare a pointer to an incomplete type and pass it around. It does not let you dereference it, index through it, or take sizeof it. So stack_t* s compiles in main.c, and s->count does not:

main.c:22:29: error: invalid use of incomplete typedef ‘stack_t’ {aka ‘struct stack’}
   22 |     printf("count: %zu\n", s->count);
      |                             ^~
cppreference: “An incomplete type is an object type that lacks sufficient information to determine the size of the objects of that type.” A struct “of unknown content” is one of the three kinds. Type, Incomplete types. Beej covers the same rule and the error messages it produces in chapter 35, Incomplete Types.

This is called an opaque struct: a struct whose members are visible only inside its own .c file. The point is not secrecy. The point is that stack.c can change its members later (a linked list instead of an array, an extra count) and no client needs to change or even recompile with care, because no client could have touched a member. Every function the client needs is a prototype in the header, named with the module prefix: stack_new, stack_push, stack_free, like lesson 4's words_find. CS107's style guide asks for exactly this typedef-and-prototype shape*.

One consequence for the client: it cannot put a stack_t on its own stack frame, because it does not know the size. It can only hold a stack_t*. So the struct must be created on the heap, by the module, in stack_new:

#define INITIAL_CAPACITY 2

stack_t* stack_new(void) {
    stack_t* s = malloc(sizeof *s);              /* block A */
    if (s == NULL) {
        return NULL;
    }
    s->items = malloc(INITIAL_CAPACITY * sizeof *s->items);   /* block B */
    if (s->items == NULL) {
        free(s);                                 /* undo block A */
        return NULL;
    }
    s->count = 0;
    s->capacity = INITIAL_CAPACITY;
    return s;
}

sizeof *s works inside stack.c because there the type is complete. If block B fails, block A is already ours and must be freed before returning NULL: the partial-cleanup rule from lesson 4.

Push: check, grow, then write

Start with capacity 2 and push five values. Watch the block:

push 10   count 0 < cap 2      write items[0]        count 1
push 20   count 1 < cap 2      write items[1]        count 2
push 30   count 2 == cap 2     GROW to 4, then write items[2]   count 3
push 40   count 3 < cap 4      write items[3]        count 4
push 50   count 4 == cap 4     GROW to 8, then write items[4]   count 5

The order inside push is fixed: check whether the block is full, grow if so, and only then write. Write first and the third push lands one slot past the end of an 8-byte block. AddressSanitizer names that exactly (you will see it in the experiments).

Growing is a realloc, and lesson 3's rule applies: catch the result in a temporary pointer. On success the block may have moved, and the old pointer is dead; assign the new one. On failure realloc returns NULL and the old block is untouched and still ours. Had we written s->items = realloc(s->items, ...), a failure would overwrite our only pointer to block B with NULL, and block B would leak.

cppreference, realloc: “On failure, returns a null pointer. The original pointer ptr remains valid and may need to be deallocated.” And on success: “The original pointer ptr is invalidated and any access to it is undefined behavior (even if reallocation was in-place).” realloc. Beej shows the same temporary-pointer pattern in 12.5, Changing Allocated Size with realloc(). 
/* Double the capacity. Returns 1 on success.
   On failure, returns 0 and the stack still owns its old block. */
static int stack_grow(stack_t* s) {
    size_t new_capacity = s->capacity * 2;
    int* bigger = realloc(s->items, new_capacity * sizeof *bigger);
    if (bigger == NULL) {
        return 0;                    /* s->items, count, capacity unchanged */
    }
    s->items = bigger;               /* ownership moved to the new block */
    s->capacity = new_capacity;
    return 1;
}

int stack_push(stack_t* s, int value) {
    if (s->count == s->capacity && !stack_grow(s)) {
        return 0;                    /* stack intact, value not pushed */
    }
    s->items[s->count] = value;
    s->count++;
    return 1;
}

stack_grow is static: a helper that only stack.c can call, and not part of the header. That is the decomposition CS107 asks for: push says what happens, grow says how the block gets bigger.

Why double, not add one. Growing by one slot would copy the whole block on every push: 1 + 2 + 3 + ... + n copies, about n²/2. Doubling from 2 copies 2 ints at the first grow, 4 at the second, 8 at the third; pushing n values copies fewer than n ints in total. Sedgewick and Wayne state the result for this exact design: “The push and pop operations take constant amortized time”*. Amortised means averaged over the whole sequence of pushes: one push may copy the block, but n pushes cost about n work altogether. Their version also halves the block when it drops to one-quarter full*; this lesson leaves that out, so pop never reallocates.

Pop and peek: a status, and a value written through an address

What should stack_pop return on an empty stack? Every int is a legal stack value, so no int is free to mean “nothing”. Split the two answers: return an int status, and write the value through a pointer the caller supplies. That is lesson 5's swap_ints move: to change the caller's variable, receive its address.

int stack_pop(stack_t* s, int* out) {
    if (s->count == 0) {
        return 0;                    /* empty: *out untouched */
    }
    s->count--;
    *out = s->items[s->count];       /* the old top, now just past count */
    return 1;
}

int stack_peek(const stack_t* s, int* out) {
    if (s->count == 0) {
        return 0;
    }
    *out = s->items[s->count - 1];
    return 1;
}

Pop does not clear the slot and does not shrink the block. Dropping count by one is what removes the value; the next push overwrites it. stack_peek and stack_count take const stack_t* because they only read. In main, the status return makes the loop that empties the stack a one-liner: while (stack_pop(s, &value)).

Free from the inside out

Two blocks, freed in the reverse order of the pointers that reach them. Block B is reached through block A, so B goes first:

void stack_free(stack_t* s) {
    if (s == NULL) {
        return;                      /* like free(NULL): a no-op */
    }
    free(s->items);                  /* block B, through A */
    free(s);                         /* block A */
}

Swap the two lines and the second one reads s->items out of a block that was freed one line earlier: a use-after-free. gcc 13 spots this particular one at compile time (-Wuse-after-free), and AddressSanitizer catches it at run time either way. After stack_free(s) returns, s in main is a dangling pointer; do not touch it again.

The interface

stack.h

#pragma once

#include <stddef.h>

/* A last-in, first-out stack of ints. The members are private to stack.c. */
typedef struct stack stack_t;

/* Create an empty stack on the heap. Returns NULL if allocation fails.
   The caller owns the result and must pass it to stack_free. */
stack_t* stack_new(void);

/* Free the stack and everything it owns. Accepts NULL. Consumes ownership. */
void stack_free(stack_t* s);

/* Push value on top. Returns 1 on success.
   On allocation failure, returns 0 and leaves the stack unchanged. */
int stack_push(stack_t* s, int value);

/* Remove the top value and write it to *out. Returns 1 if a value was popped.
   On an empty stack, returns 0 and leaves *out unchanged. */
int stack_pop(stack_t* s, int* out);

/* Copy the top value to *out without removing it. Returns 1 if there is one.
   On an empty stack, returns 0 and leaves *out unchanged. */
int stack_peek(const stack_t* s, int* out);

/* Number of values currently on the stack. */
size_t stack_count(const stack_t* s);

Read the contracts once more. Each one says what happens on the bad path: NULL, 0, untouched. A client can act on that without reading stack.c, which is the whole point of the header.

Do it, from memory

  1. Create and enter the exercise folder:

    cd ~/workspace/brushup-c
mkdir -p exercises/09-stack && cd exercises/09-stack

  2. Create stack.h exactly as shown. Paste the setup Makefile.

  3. Write stack.c: the struct, a named constant for the initial capacity of 2, a static grow helper, and the six functions. Close this page first and write from the invariants and the contracts. Reopen only if you are stuck for more than a few minutes.

  4. Write main.c. Declare the source data once, as a named constant array of five ints: 10 20 30 40 50. Create a stack and check it. Push the five values in order; if a push fails, free the stack and return 1. Print the count. Peek and print the top. Then pop in a loop, printing each value with a leading space after a popped: label, and end the line. Print the count again. Attempt one more pop and print whether the stack was empty. Free the stack and return 0. Expected:

    count: 5
peek: 50
popped: 50 40 30 20 10
count: 0
empty: yes

    With capacity 2, this run grows the block twice: at the third push and at the fifth. The CS107 testing guide asks for the minimal case and the fringe*: the pop on an empty stack is the minimal case, and the two grows are the fringe of the block.

  5. Run make, ./stack, and make check. Require no warnings, the exact five lines, and no Valgrind errors or leaks. Valgrind should count 5 allocs and 5 frees: the struct, the first items block, two realloc grows, and one buffer for printf.

  6. Break it three ways, one at a time.

    1. In stack_push, move the line that writes s->items[s->count] above the grow check. Build and run. Read which push overflows, and by how many bytes past which region. Restore it.
    2. In stack_free, swap the two free calls. Build: read the gcc warning. Run: read the AddressSanitizer timeline (the bad read, the earlier free, the allocation). Restore it.
    3. In main.c, replace one stack_count(s) with s->count. Build. Read the error, and notice that it is the compiler, not the sanitizer, that stops you. Restore it.

  7. Optional, plain build only: make realloc fail. In stack_grow, temporarily ask for (size_t)1 << 62 bytes instead of the real size. In main, print push N failed, count still C before freeing on a failed push. Run make check (the sanitizer build aborts on a request that large, so use the plain build under Valgrind). You should see push 30 failed, count still 2 and 0 errors, no leaks: the stack survived. Now write the grow without the temporary pointer, s->items = realloc(s->items, ...), and run make check again: 8 bytes in 1 blocks are definitely lost, allocated in stack_new. Restore both.

  8. Restore the correct program and run all three commands once more. Then tell me: lesson 9 done.

Reading the three reports

Write before grow. The first two pushes fit. The third writes slot 2 of a block that holds two ints:

ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 4 ...
    #0 ... in stack_push stack.c:...
    #1 ... in main main.c:...
0x... is located 0 bytes after 8-byte region
allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in stack_new stack.c:...

Two ints × four bytes explain the 8-byte region. “0 bytes after” is the off-by-one signature from lesson 1. The allocation site is stack_new, so the block that overflowed is block B at its first size: the grow had not happened yet.

Struct freed before items. gcc says it first:

stack.c: In function ‘stack_free’:
stack.c:33:11: warning: pointer ‘s’ used after ‘free’ [-Wuse-after-free]
   33 |     free(s->items);
      |          ~^~~~~~~

Run it anyway and AddressSanitizer gives the timeline:

ERROR: AddressSanitizer: heap-use-after-free
READ of size 8 ...
    #0 ... in stack_free stack.c:...
0x... is located 0 bytes inside of 24-byte region
freed by thread T0 here:
    #0 ... in free
    #1 ... in stack_free stack.c:...
previously allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in stack_new stack.c:...

“READ of size 8” is the pointer items being loaded; “24-byte region” is block A, the struct. The read, the free and the allocation are three lines apart in your own code.

Client reaches inside. No run at all:

main.c: In function ‘main’:
main.c:22:29: error: invalid use of incomplete typedef ‘stack_t’ {aka ‘struct stack’}

This is the cheapest of the three. The header made the promise, and the compiler enforces it on every client, every build.

Read next

Everything here is C, except the last item, which is pure theory. Read in this order; the first item is three short source files, not a chapter.

  1. An array stack in C that does not grow. Mark Allen Weiss, Data Structures and Algorithm Analysis in C, 2nd ed., stackar.h, stackar.c and teststka.c (the author publishes the book's source files free). The header hides the struct the same way yours does: struct StackRecord; is an incomplete type, and the client only ever holds a pointer. Two differences to look for. His typedef hides the pointer too (typedef struct StackRecord *Stack;), so a client cannot tell that Stack is an address; yours keeps the * visible. And his stack has a fixed capacity: CreateStack(MaxElements) allocates once, IsFull compares against it, and Push on a full stack calls Error instead of growing. Read Push, Pop and TopAndPop against your own and note that his top is an index that starts at -1, where yours is a count that starts at 0. DisposeStack frees the array before the record, the same inside-out order as your stack_free. The test program creates a stack of 12, pushes 0 to 9, then prints and pops until empty. It never tries the pop on an empty stack; yours does.

  2. The grow step, and the module split. Beej, 12.5 Changing Allocated Size with realloc(), including 12.5.1. The first example catches realloc in new_p, tests it for NULL, and only then assigns it to p: your stack_grow exactly. The readline example in 12.5.1 is a growing buffer in a loop, bufsize *= 2 then realloc through new_buf, and it ends with a shrink-to-fit that your stack leaves out. Then chapter 17, Multifile Projects: 17.1 on prototypes in headers, 17.2 on include guards (the long form of your #pragma once), and 17.3 on static, the keyword that keeps stack_grow out of the header. For the rule behind the opaque struct, chapter 35, Incomplete Types; 35.2 lists the error messages, and 35.5 shows a struct being completed later in the same file, which is what stack.c does.

  3. The same ideas in CS50's C. CS50x, Week 5 notes, Stacks and the Arrays section that follows it. The stack there is a struct with a fixed CAPACITY array and a size; the notes say outright that it would be nice if it could grow, then show a list going from three ints to four, first by malloc, copy and free, then by realloc caught in int *tmp. That is one grow step of your stack, written out in main with no struct around it. If you prefer to watch first, the CS50 Short Stacks (Doug Lloyd) draws the array version with a top index, pushed and popped by hand, then the linked-list version. The array version keeps the struct on the caller's frame and passes &s, which your header forbids. The linked-list version hands a head pointer back and forth, list = push(list, 12); hold that shape until lesson 10.

  4. Why doubling costs so little. MIT 6.006, Fall 2011, Lecture 9 notes, Table Doubling, page 2, the part headed “How fast to grow?”. No code, two lines of arithmetic. Growing by one slot costs 1 + 2 + ... + n, which is order n². Doubling costs 1 + 2 + 4 + 8 + ... + n, which is order n. The notes are about hash tables, and the sum is the same for your items block. The paragraph headed “Amortized Analysis” under it is the definition of the word, with a rent-versus-daily-cost picture.

Where this lands in CS107. Lecture 7 (Stack and Heap) is where realloc is introduced*. The slides write str = realloc(str, ...) and then assert(str != NULL): the direct assignment this lesson told you not to write. It is fine there because an assert aborts the program on failure, so nothing survives to leak. Your stack promises to survive a failed push, so it needs the temporary pointer. Lecture 8 (Generic Operations) introduces void*, which is how a stack like this one comes to hold any type. Not needed for this lesson. The course style guide asks for the typedef form you used, and its testing guide is where the minimal-case-and-fringe rule behind your test program comes from.
