Halve, Then Merge

Merge sort and quicksort split a range and call themselves on each half. Each call gets its own stack frame; the array and one scratch block stay on the heap, owned by exactly one function.

About 45 minutes Where: WSL, exercises/06-recursive-sorts/ Mission · Cheat sheet · Lesson 5
Your win today. Write both recursive sorts from a blank file, with a merge that borrows one heap scratch block allocated by a wrapper, a partition that returns the pivot's final index, and base cases that cannot loop forever on size_t.

A call gets its own frame

Eight ints live in a heap block at, say, 0x5030…70. A function is asked to sort the half-open range [0, 8) of that block. It splits the range at 4, calls itself on [0, 4), and that call splits again. At the deepest point the stack looks like this:

stack (newest frame at the bottom)      every frame has its own lo and hi
main                a = 0x5030…70                    owner of the array
merge_sort          a = 0x5030…70  n = 8  scratch = 0x5030…a0   owner of scratch
merge_sort_range    a = 0x5030…70  lo = 0  hi = 8  scratch
merge_sort_range    a = 0x5030…70  lo = 0  hi = 4  scratch
merge_sort_range    a = 0x5030…70  lo = 0  hi = 2  scratch
merge_sort_range    a = 0x5030…70  lo = 0  hi = 1  scratch      one element: return

Every argument is copied into the callee's frame. Beej puts it bluntly: “EVERYTHING you pass to a function WITHOUT EXCEPTION is copied into its corresponding parameter”. So lo and hi are private to each frame, and the frame above keeps its own values while the one below works. The pointer a is also a copy, but every copy holds the same address, so every frame writes into the same heap block. That is the whole trick: private indices on the stack, one shared array on the heap.

Beej, 4.1 Passing by Value. The CS107 GDB guide shows the same picture from the debugger: in a backtrace “each line represents a stack frame (ie. a function call)” (GDB Guide).

The base case counts elements, not endpoints. The range [lo, hi) holds hi - lo elements. That subtraction is safe on size_t because lo <= hi always holds: the split puts mid between them, and the two calls receive [lo, mid) and [mid, hi). A range of zero or one element is already sorted, so:

if (hi - lo < 2) {
    return;
}

Two ways to get this wrong. if (lo == hi) stops only on the empty range; a range of one element splits into [lo, lo) and [lo, lo + 1), and the second call is the same call again, forever. if (hi - 1 <= lo) subtracts from an index that can be 0 and wraps, the same trap as lesson 5's mid - 1. Test the count.

Merge sort: halve, sort each half, merge

Start with the eight values 9 4 15 9 26 5 35 4. Split at the midpoint, sort each half by the same method, then merge the two sorted halves:

[0, 8)   9 4 15 9 | 26 5 35 4
[0, 4)   9 4 | 15 9          [4, 8)   26 5 | 35 4
[0, 2)   9 | 4   -> 4 9      [4, 6)   26 | 5  -> 5 26
[2, 4)   15 | 9  -> 9 15     [6, 8)   35 | 4  -> 4 35
[0, 4)   merge 4 9 + 9 15    -> 4 9 9 15
[4, 8)   merge 5 26 + 4 35   -> 4 5 26 35
[0, 8)   merge 4 9 9 15 + 4 5 26 35  -> 4 4 5 9 9 15 26 35

Each level of the tree touches all n elements once, and there are about log₂ n levels. Sedgewick and Wayne state the bound: top-down mergesort uses “between ½ N lg N and N lg N compares and at most 6 N lg N array accesses to sort any array of length N”, and it does so no matter what the input.

Sedgewick and Wayne, 2.2 Mergesort. The same page names the cost: “its prime disadvantage is that it uses extra space proportional to N.” That extra space is the scratch block below.

The merge is the only real work. Walk the two runs with one index each, always taking the smaller head, into a scratch area. Ties take the left run, which keeps equal keys in their original order. When one run runs out, copy the rest of the other:

left  a[0..4) = 4 9 9 15      right  a[4..8) = 4 5 26 35
i=0 j=4   4 < 4 ? no   take left   scratch[0] = 4     i=1
i=1 j=4   4 < 9 ? yes  take right  scratch[1] = 4     j=5
i=1 j=5   5 < 9 ? yes  take right  scratch[2] = 5     j=6
i=1 j=6   26 < 9 ? no  take left   scratch[3] = 9     i=2
i=2 j=6   26 < 9 ? no  take left   scratch[4] = 9     i=3
i=3 j=6   26 < 15 ? no take left   scratch[5] = 15    i=4   left run empty
          copy the rest of right   scratch[6] = 26  scratch[7] = 35
          copy scratch[0..8) back into a[0..8)
/* Merge the sorted runs a[lo..mid) and a[mid..hi) via scratch[lo..hi). */
static void merge(int* a, size_t lo, size_t mid, size_t hi, int* scratch) {
    size_t i = lo;                  /* next unused in the left run */
    size_t j = mid;                 /* next unused in the right run */
    size_t k = lo;                  /* next free slot in scratch */
    while (i < mid && j < hi) {
        if (a[j] < a[i]) {
            scratch[k++] = a[j++];
        } else {
            scratch[k++] = a[i++];  /* ties take the left run */
        }
    }
    while (i < mid) { scratch[k++] = a[i++]; }
    while (j < hi)  { scratch[k++] = a[j++]; }
    for (k = lo; k < hi; k++) {
        a[k] = scratch[k];          /* copy back exactly [lo, hi) */
    }
}

Where does scratch live, and who frees it? The merge needs hi - lo ints of room. The lazy answer is malloc inside merge: for eight elements that is seven allocations and seven frees, and each of them can fail halfway through a sort. The right answer is one block of n ints, allocated once by a top-level wrapper, passed down as a parameter, and freed by that same wrapper. Sedgewick and Wayne do exactly this: their public sort allocates aux once and hands it to the recursive sort(a, aux, lo, hi), and they warn that a static scratch array “is inadvisable in library software because multiple clients might use the class concurrently”.

Merge.java: Comparable[] aux = new Comparable[a.length]; sort(a, aux, 0, a.length-1);. Java frees aux for them. In C the wrapper is the owner and must call free. 
/* Sort a[lo..hi). scratch has room for at least hi ints. */
static void merge_sort_range(int* a, size_t lo, size_t hi, int* scratch) {
    if (hi - lo < 2) {
        return;
    }
    size_t mid = lo + (hi - lo) / 2;
    merge_sort_range(a, lo, mid, scratch);
    merge_sort_range(a, mid, hi, scratch);
    merge(a, lo, mid, hi, scratch);
}

void merge_sort(int* a, size_t n) {
    if (n < 2) {
        return;
    }
    int* scratch = malloc(n * sizeof *scratch);
    if (scratch == NULL) {
        return;                     /* a is left as it was */
    }
    merge_sort_range(a, 0, n, scratch);
    free(scratch);                  /* the owner frees, once */
}

Read the ownership like lesson 3. merge_sort owns scratch: it allocates, checks for NULL, and frees. Every merge_sort_range and merge frame is a borrower: they receive the pointer, write through it, and never free it. The wrapper is also why the interface stays clean: main calls merge_sort(a, n) and never learns that a scratch block exists. The recursive function with its extra lo, hi, scratch parameters is static in sort.c, not in the header.

cppreference, malloc: “On success, returns the pointer to the beginning of newly allocated memory. To avoid a memory leak, the returned pointer must be deallocated with free() or realloc(). On failure, returns a null pointer.”

Quicksort: partition, then sort both sides in place

Quicksort splits differently. It picks one value, the pivot, and rearranges the range so that everything left of the pivot is no larger and everything right of it is no smaller. The pivot is then in its final place and never moves again. Both sides are sorted by the same method. Nothing is copied anywhere, so there is no scratch block and no wrapper allocation.

Take the same eight values and pivot on a[lo] = 9. Two indices scan towards each other. i walks right and stops on a value that is not smaller than the pivot; j walks left and stops on a value that is not larger. When both have stopped and i < j, swap and continue:

pivot 9      9  4  15  9  26  5  35  4
i=1 j=7      i stops at a[2]=15; j stops at a[7]=4          swap
             9  4  4  9  26  5  35  15
i=3 j=6      i stops at a[3]=9  (equal to pivot: stop!)
             j stops at a[5]=5                              swap
             9  4  4  5  26  9  35  15
i=4 j=4      i stops at a[4]=26; j walks 35, 26, stops at a[3]=5
             i=4 >= j=3: crossed, stop
swap a[lo] with a[j]:
             5  4  4  9  26  9  35  15
             ^ <= 9 ^  [9]  ^ >= 9 ^          return 3

The line marked stop! matters. Sedgewick and Wayne: “It is best to stop the left scan for items with keys greater than or equal to the partitioning item's key and the right scan for items less than or equal to the partitioning item's key.” Skipping over equal keys looks harmless and makes the sort quadratic on inputs full of duplicates. The data has two 9s and two 4s so that you can see the stop happen.

Sedgewick and Wayne, 2.3 Quicksort: after partitioning, “the entry a[j] is in its final place in the array, for some j”; quicksort “is in-place (uses only a small auxiliary stack)”; it “uses ~N²/2 compares in the worst case, but random shuffling protects against this case.” This lesson skips the shuffle; on eight values it does not matter. 
/* Partition a[lo..hi) around the pivot a[lo]. hi - lo must be at least 1.
   Returns the pivot's final index p: a[lo..p) <= pivot <= a[p+1..hi). */
static size_t partition(int* a, size_t lo, size_t hi) {
    int pivot = a[lo];
    size_t i = lo + 1;              /* scans right, stops on >= pivot */
    size_t j = hi - 1;              /* scans left, stops on <= pivot */
    for (;;) {
        while (i < hi && a[i] < pivot) {
            i++;
        }
        while (a[j] > pivot) {
            j--;                    /* a[lo] == pivot stops this at lo */
        }
        if (i >= j) {
            break;
        }
        swap_ints(&a[i], &a[j]);
        i++;
        j--;
    }
    swap_ints(&a[lo], &a[j]);       /* pivot into its final slot */
    return j;
}

static void quick_sort_range(int* a, size_t lo, size_t hi) {
    if (hi - lo < 2) {
        return;
    }
    size_t p = partition(a, lo, hi);
    quick_sort_range(a, lo, p);     /* [lo, p): left of the pivot */
    quick_sort_range(a, p + 1, hi); /* [p+1, hi): right of the pivot */
}

void quick_sort(int* a, size_t n) {
    quick_sort_range(a, 0, n);
}

Two size_t details. The i scan needs i < hi because every value after the pivot may be smaller than it. The j scan needs no j > lo guard because a[lo] is the pivot itself, and a scan that stops on values <= pivot cannot walk past it. Change the pivot choice and that guard becomes necessary. The swap is lesson 5's swap_ints, called with two addresses into the same block. The pivot's index p is excluded from both recursive calls: [lo, p) and [p + 1, hi) are each strictly smaller than [lo, hi), which is what guarantees the recursion ends.

The interface

sort.h

#pragma once

#include <stddef.h>

/* Exchange the two ints at a and b. */
void swap_ints(int* a, int* b);

/* Return 1 if the n ints at a are in ascending order, else 0. */
int is_sorted(const int* a, size_t n);

/* Sort the n ints at a into ascending order using one heap scratch block
   of n ints, allocated and freed inside. If that block cannot be
   allocated, a is left unchanged. */
void merge_sort(int* a, size_t n);

/* Sort the n ints at a into ascending order, in place. */
void quick_sort(int* a, size_t n);

Four public functions. The recursive workers merge_sort_range, merge, partition and quick_sort_range are static in sort.c and appear nowhere in the header. A client sees (a, n) and nothing about ranges or scratch.

Reading the three reports

1. Copy-back off by one. The top-level merge has hi = 8. k <= hi reads scratch[8], one int past the 32-byte block:

ERROR: AddressSanitizer: heap-buffer-overflow on address 0x503000000090 ...
READ of size 4 ...
    #0 ... in merge sort.c:40
    #1 ... in merge_sort_range sort.c:52
    #2 ... in merge_sort_range sort.c:51
0x503000000090 is located 0 bytes after 32-byte region
allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in merge_sort sort.c:59
    #2 ... in main main.c:35

The read fires before the matching write to a[8], so the report blames the scratch block, allocated in merge_sort. It is the same “0 bytes after” shape as lesson 1's off-by-one. New here: the frames under merge are two merge_sort_range frames at different line numbers: the one that called merge, under the one that made the recursive call on [mid, hi). That is the tree from the trace, read bottom-up.

2. Scratch never freed. Under make check:

==12345== 32 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x...: malloc (in .../vgpreload_memcheck-amd64-linux.so)
==12345==    by 0x...: merge_sort (sort.c:59)
==12345==    by 0x...: main (main.c:35)
==12345== LEAK SUMMARY:
==12345==    definitely lost: 32 bytes in 1 blocks
...
==12345== ERROR SUMMARY: 1 errors from 1 contexts
make: *** [Makefile:14: check] Error 1

Thirty-two bytes, one block, allocated in the wrapper, never freed. Under the sanitizer build this particular leak is also reported (“LeakSanitizer: detected memory leaks, Direct leak of 32 byte(s)”), unlike lesson 1's. The difference: here the only copy of scratch lived in merge_sort's frame, and the quicksort calls that followed overwrote that dead frame, so no stale pointer survived for the exit-time scan to find. Do not rely on that. make check is the gate for leaks.

3. Base case that never fires. A one-element range calls itself on the same one-element range. Each call pushes a new frame until the stack (8 MB by default) is exhausted:

AddressSanitizer:DEADLYSIGNAL
ERROR: AddressSanitizer: stack-overflow on address 0x7ffed3462ff8 ...
    #0 ... in merge_sort_range sort.c:50
    #1 ... in merge_sort_range sort.c:51
    #2 ... in merge_sort_range sort.c:51
    #3 ... in merge_sort_range sort.c:51
    ... (thousands more, all the same line)
SUMMARY: AddressSanitizer: stack-overflow sort.c:50 in merge_sort_range

Every frame below the first is the same function at the same line: the second recursive call, the one on [mid, hi), because [lo, lo + 1) has mid == lo and calls itself on [lo, lo + 1) again. That column is the signature of a base case that does not shrink the problem. When you see it, print lo and hi at the top of the function, or walk one element by hand, and ask which range calls itself unchanged.

Read next

Everything here is C. Read in this order; the first two items are one source file, not chapters.

  1. Merge sort in C. Mark Allen Weiss, Data Structures and Algorithm Analysis in C, 2nd ed., sort.c, the three functions Mergesort, MSort and Merge (the author publishes the book's source files free). This is your wrapper, range sort and merge in closed form: int Left, Right, base case if (Left < Right), split at Center with calls on [Left, Center] and [Center + 1, Right]. Look at Mergesort: it calls malloc once for TmpArray, hands it down, and frees it after MSort returns. Same ownership as your merge_sort. Two differences to notice. On a failed malloc Weiss calls FatalError and stops the program; you return and leave a untouched. His Merge takes Lpos, Rpos, RightEnd and copies back by walking RightEnd down for NumElements steps; you copy exactly [lo, hi). Ties go left in both: his A[Lpos] <= A[Rpos] is your a[j] < a[i] read the other way round.

  2. Quicksort in C. Same file, Quicksort, Qsort and Median3. Three things you did not write. The pivot is the median of A[Left], A[Center] and A[Right], and Median3 parks it at Right - 1. Ranges shorter than Cutoff go to InsertionSort instead of recursing. And the scans are while (A[++i] < Pivot) and while (A[--j] > Pivot), with no bounds test at all: Median3 has already put a value <= pivot at Left and the pivot itself at Right - 1, so each scan hits a stopper before it can leave the range. Your i < hi guard exists because your pivot is a[lo] and nothing protects the right end. Both versions stop on equal keys. The file also keeps a second scan loop under #if 0, labelled as Figure 7.15 and as code that does not work. Work out on paper why: start both scans on a value equal to the pivot.

  3. Frames. Beej, 4.1 Passing by Value. One page with one example: increment(i) changes its copy and main's i stays 10. That is why every merge_sort_range frame keeps its own lo and hi. Then the CS107 GDB Guide, the Backtrace and Stack Frames parts: run your sort under gdb, break in merge, type backtrace, and compare the listing with the frame picture at the top of this lesson. up and down move between frames.

  4. If you prefer to watch first. CS50 Shorts: Recursion, Call Stacks and Merge Sort, from Harvard's C-based introductory course. Recursion covers the base case and the recursive case; Call Stacks shows frames being pushed and popped; Merge Sort walks the halving and merging by hand. Watch Call Stacks before Recursion if the frame picture is still fuzzy.

Ask your teacher. If you are unsure who frees a block that a recursive function uses, ask before you write the free. The answer is the function that called malloc, unless it handed ownership on, as copy_of_data hands it to main. If that is not obvious from the code, the code needs a wrapper.
