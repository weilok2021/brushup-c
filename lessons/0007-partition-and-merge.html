What a partition is

Take this array. Pick the leftmost item, 9, and call it the pivot.

To partition on 9 means to rearrange the array so that three things hold:

The definition and the four-arrays question are from the CS61B textbook, 30.1 Partitioning: “x moves to some position j”, “All array elements to the left of x are less than or equal to x”, “All array elements to the right of x are greater than or equal to x”.
  • 9 moves to some index p.
  • Every item left of p is <= 9.
  • Every item right of p is >= 9.

Neither side has to be sorted. Four arrangements of the same numbers, pivot shaded. Three are valid partitions on 9. One is not. Find it before you open the answer.

Answer

D. The 4 at index 3 is smaller than 9 and sits to the pivot's right. A, B and C each have nothing larger than 9 on the left and nothing smaller on the right. The second 9 may sit on either side.

Why do this? Sorted, the array is 4 4 5 9 9 15 26 35. Every valid partition lands the pivot at index 3 or 4, exactly where a 9 sits in the sorted array. The pivot is in its final place and never moves again.

Quicksort is three lines: partition on the leftmost item, quicksort the left half, quicksort the right half. Today you write the partition only. Lesson 8 adds the two recursive calls.

CS61B textbook, 30.2 Quicksort Algorithm: “To quicksort N items: Partition on the leftmost item as the pivot. Recursively quicksort the left half. Recursively quicksort the right half.”

Hoare's partition: L and G

Tony Hoare's scheme: two pointers walk toward each other. CS61B states it in six rules, and the demo follows them exactly:

Josh Hug's Hoare partitioning demo (Google Slides, 18 slides): “L pointer is a friend to small items, and hates large or equal items. G pointer is a friend to large items, and hates small or equal items. Walk pointers towards each other, stopping on a hated item. When both pointers have stopped, swap and move pointers by one. When pointers cross, you are done walking. Swap pivot with G.” The captions in the demo below borrow its voice. Same rules in prose: CS61B textbook, 32.1, Tony Hoare's Partitioning.
  • Create L and G pointers at the left and right ends. L starts just right of the pivot.
  • L is a friend to small items, and hates large or equal items.
  • G is a friend to large items, and hates small or equal items.
  • Walk the pointers toward each other, stopping on a hated item.
  • When both have stopped, swap, and move both pointers by one.
  • When the pointers cross, you are done walking. Swap the pivot with G.

Small means smaller than the pivot; large means larger. In C, L is i and G is j. Click Next and read what each pointer says about the item under it.

pivot   L walked past it: <= pivot   G walked past it: >= pivot

The same rules, in C

/* Partition a[lo..hi) around the pivot a[lo]. hi - lo must be at least 1.
   Returns the pivot's final index p: a[lo..p) <= a[p] <= a[p+1..hi). */
size_t partition(int* a, size_t lo, size_t hi) {
    int pivot = a[lo];
    size_t i = lo + 1;              /* L: starts just right of the pivot */
    size_t j = hi - 1;              /* G: starts at the right end */
    for (;;) {
        while (i < hi && a[i] < pivot) {
            i++;                    /* L walks while it loves what it sees */
        }
        while (a[j] > pivot) {
            j--;                    /* G walks while it loves what it sees */
        }
        if (i >= j) {
            break;                  /* crossed: done walking */
        }
        swap_ints(&a[i], &a[j]);   /* both stopped: swap ... */
        i++;
        j--;                        /* ... and move both by one */
    }
    swap_ints(&a[lo], &a[j]);       /* swap the pivot with G */
    return j;
}

Each rule is one line. “Hates large or equal” is the strict < in L's loop. Three questions the demo has already answered.

Why does L need i < hi and G no guard at all?

On 9 1 2 3, L never meets a large or equal item. It walks to hi and stops there only because of the guard. G always meets one: the pivot itself sits at a[lo], and G hates equal items. Pick the pivot from anywhere else and G needs a guard too.

Why “or equal”?

Six 7s. Equal counted as hated: both pointers stop at every item, swap sevens with sevens, and meet in the middle. The pivot lands at 3. With the planted bug, L walks to the end and the pivot lands at 5. Quicksort then gets a side of five and a side of none, at every level: about n²/2 compares for n equal keys.

Sedgewick and Wayne, 2.3 Quicksort: “It is best to stop the left scan for items with keys greater than or equal to the partitioning item's key and the right scan for items less than or equal to the partitioning item's key.” Hoare's scheme with these stops stays balanced on all-equal keys (Wikipedia).

Why move both pointers by one after a swap?

After the swap, L stands on a small item and G on a large one. Each loves what it now sees, so stepping past it skips one comparison and changes nothing.

The promise, and a checker

Write the definition down as a postcondition and it becomes something a program can test: partition(a, lo, hi) returns p with a[lo..p) <= a[p] <= a[p+1..hi). That is lesson 6b's habit: say what must be true, then check it.

int is_partitioned(const int* a, size_t lo, size_t hi, size_t p) {
    for (size_t k = lo; k < p; k++) {
        if (a[k] > a[p]) {
            return 0;               /* something large on the left */
        }
    }
    for (size_t k = p + 1; k < hi; k++) {
        if (a[k] < a[p]) {
            return 0;               /* something small on the right */
        }
    }
    return 1;
}

One limit. The checker says yes to a pivot at index 5 on six 7s, because equal keys may sit on either side. Only the landing index tells a correct partition from a bad one.

Merge: the smallest item is at the front of one run

Merge sort's step is the reverse problem. The two halves are already sorted, and one pass combines them. The smallest item of both runs must be at the front of one of them. Compare the two fronts, copy the smaller one into scratch, and repeat until one run is empty. Then copy the rest of the other run.

CS61B textbook, 15.4 Mergesort: “The smallest element must be at the start of one of the two lists. So let's compare those, and put the smallest element at the start of our new list. … We can continue comparing the first two elements and moving the smallest into place until one list is empty, then copy the rest of the other list over into the end of the new list.” Hug's merge sort demo draws it with an Aux row, as here.

Every step of this run, as a list

Ties take the left run. That keeps equal keys in their original order, which lesson 8 will call stable.

/* Merge the sorted runs a[lo..mid) and a[mid..hi) via scratch[lo..hi). */
void merge(int* a, size_t lo, size_t mid, size_t hi, int* scratch) {
    size_t i = lo;                  /* front of the left run */
    size_t j = mid;                 /* front of the right run */
    size_t k = lo;                  /* next free slot in scratch */
    while (i < mid && j < hi) {
        if (a[j] < a[i]) {
            scratch[k++] = a[j++];  /* right front is smaller */
        } else {
            scratch[k++] = a[i++];  /* left front is smaller, or a tie */
        }
    }
    while (i < mid) { scratch[k++] = a[i++]; }   /* one of these two loops */
    while (j < hi)  { scratch[k++] = a[j++]; }   /* copies the leftover run */
    for (k = lo; k < hi; k++) {
        a[k] = scratch[k];          /* copy back exactly [lo, hi) */
    }
}

merge borrows scratch: it writes through the pointer and never frees it. Today main owns the block. In lesson 8 a merge_sort wrapper owns it, and merge does not change.

The interface

partition.h

#pragma once

#include <stddef.h>

/* Exchange the two ints at a and b. */
void swap_ints(int* a, int* b);

/* Return 1 if the n ints at a are in ascending order, else 0. */
int is_sorted(const int* a, size_t n);

/* Rearrange a[lo..hi) around the pivot a[lo]. The range must hold at least
   one element. Returns the pivot's final index p, with
   a[lo..p) <= a[p] <= a[p+1..hi). */
size_t partition(int* a, size_t lo, size_t hi);

/* Return 1 if a[lo..p) <= a[p] <= a[p+1..hi), else 0. */
int is_partitioned(const int* a, size_t lo, size_t hi, size_t p);

/* Merge the sorted runs a[lo..mid) and a[mid..hi) into ascending order,
   using scratch[lo..hi) as workspace. scratch is borrowed, never freed. */
void merge(int* a, size_t lo, size_t mid, size_t hi, int* scratch);

Five functions, all public because main drives them directly. In lesson 8, partition and merge become static helpers behind quick_sort and merge_sort. The code inside them is the code you write today.

The mid row is the trap. Half-open, mid ends the left run and starts the right. Closed, the left run ends at mid and the right starts at mid + 1. Your runs are 4 9 9 15 and 4 5 26 35, so the closed call is merge(r, 0, 3, 7, scratch). Write 4 there and 4 9 9 15 4 is treated as one sorted run: no crash, and sorted: no.

No guard is needed here: neither function ever gets an empty range. Lesson 8's quicksort does. Its left call is [low, p - 1], and p - 1 wraps under size_t when the pivot lands at index 0. Guard it with if (p > low), as you guarded mid - 1 in lesson 6.

Reading the three reports

1. L loves equal items. No report, and every checker still says yes. Only the landing spot moved: the first line says pivot 9 lands at 4, the six 7s say pivot 7 lands at 5, a five-and-zero split. A correct partition can still be a bad one, and only the index shows it.

2. The missing guard. The 9 1 2 3 call walks L past 1, 2 and 3 and reads the int after the block:

Sixteen bytes is four ints: the 9 1 2 3 block. It is lesson 1's off-by-one, reached by a pointer with nothing to stop it. The first three lines printed fine because each of those ranges had a large or equal item after the pivot.

3. The right run's tail never copied. Under the sanitizer build:

merged: 4 4 5 9 9 15 -1094795586 -1094795586
sorted: no

The loop stopped when the left run emptied, so scratch[6] and scratch[7] were never written, and the copy-back moved whatever malloc left there into a. Under ASan that is the byte 0xbe repeated, which reads as -1094795586; on the plain build it is anything. Valgrind names the symptom, not the fix: “Conditional jump or move depends on uninitialised value(s)” inside printf. When Valgrind blames printf, ask which value you handed it and where it should have been written.
