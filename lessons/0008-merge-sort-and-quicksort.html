One promise, two trusts

Both sorts have the same shape. Say the promise first, in one sentence above the function, as in lesson 6b:

Promise. After sort(a, lo, hi) returns, a[lo..hi] is in ascending order.

Then the body is three lines of thought:

  1. Base case. Zero or one item is already sorted. In closed form that is lo >= hi. Return.
  2. Shrink. Make two smaller ranges. Call yourself on each and trust the promise for them.
  3. Work. Do the one thing the two trusted halves cannot do for you.

Merge sort does the work after the calls: the halves are sorted, so merge them. Quicksort does the work before: partition, and the two sides need no combining at all. Josh Hug's textbook says quicksort in three lines.

CS61B textbook, 30.2 Quicksort Algorithm: “To quicksort N items: Partition on the leftmost item as the pivot. Recursively quicksort the left half. Recursively quicksort the right half.” Merge sort is the mirror image in 15.4 Mergesort: split, sort each half, merge.

Count the merges: seven, one per split. Each level of the tree touches all eight items once, and there are three levels, so the cost is about n log n. Hug argues it exactly that way.

CS61B textbook, 15.4 Mergesort: “The top level takes ~N AU. Next level takes ~N/2 + ~N/2 = ~N. … split the array until it is length 1, so k = log₂(N). Thus the overall runtime is Θ(N log N).” 
/* Sort a[lo..hi]. Promise on return: a[lo..hi] is ascending. */
void merge_sort(int* a, size_t lo, size_t hi) {
    if (lo >= hi) {
        return;                     /* zero or one item: already sorted */
    }
    size_t mid = lo + (hi - lo) / 2;
    merge_sort(a, lo, mid);         /* trust: left half sorted */
    merge_sort(a, mid + 1, hi);     /* trust: right half sorted */
    merge(a, lo, mid, hi);          /* the work: combine them */
}

main calls it as merge_sort(a, 0, n - 1). That n - 1 is the caller's job, and it wraps when n is 0, so the header says n must be at least 1. (The usual C shape hides this behind a merge_sort(a, n) wrapper. You chose the one-function form; keep the rule in the header instead.)

merge is lesson 7's function, unchanged, now static. It copies the two runs out, merges back into a[lo..hi], and frees its two copies before it returns. Seven merges, fourteen mallocs, fourteen frees, all balanced inside one function.

The textbook alternative is one workspace of n ints allocated once by merge_sort and passed down to every merge: see Sedgewick and Wayne's Merge.java, where aux is allocated once. It saves twelve mallocs on eight items and costs a borrowed pointer in every signature. You asked for the version you can see; this is it.

Why mid + 1? Closed range: mid is the last index of the left half, so the right half starts one past it. Write mid there and a two-item range calls itself on the same two items forever. That is planted bug 1.

Why lo >= hi and not lo == hi? Merge sort never produces lo > hi, so here both work. Quicksort does produce it. Use the same guard in both and stop thinking about it.

/* Sort a[lo..hi]. Promise on return: a[lo..hi] is ascending. */
void quick_sort(int* a, size_t lo, size_t hi) {
    if (lo >= hi) {
        return;                     /* zero or one item: already sorted */
    }
    size_t p = partition(a, lo, hi);    /* the work: pivot lands at p */
    if (p > lo) {
        quick_sort(a, lo, p - 1);       /* trust: left side sorted */
    }
    quick_sort(a, p + 1, hi);           /* trust: right side sorted */
}

partition is lesson 7's function, now static. Index p is in neither call: [lo, p - 1] and [p + 1, hi] are both shorter than [lo, hi], which is what makes the recursion finite.

Why the guard if (p > lo)? When the pivot is the smallest item it lands at lo. Then p - 1 on size_t does not go to -1; it wraps to the largest possible number, and the next call reads a[] four bytes before the block. That is planted bug 2. The right call needs no guard: p + 1 is at most hi + 1, and lo >= hi catches that empty range.

Why no merge? After the partition, everything left of p is <= a[p] and everything right is >= a[p]. Sort each side in place and the whole range is in order. Nothing is copied, so quicksort allocates nothing.

CS61B textbook, 30.3 Quicksort Performance Caveats: best case Θ(N log N), worst case Θ(N²) when every pivot lands at an end. Sorted input with the leftmost pivot is exactly that worst case. Real libraries shuffle first or pick a median; this lesson does not, and on eight items it does not matter.

The interface

sort.h

#pragma once

#include <stddef.h>

/* Exchange the two ints at a and b. */
void swap_ints(int* a, int* b);

/* Return 1 if the n ints at a are in ascending order, else 0. */
int is_sorted(const int* a, size_t n);

/* Sort a[lo..hi] into ascending order. Closed range: hi is the last index,
   so a whole array of n items is (a, 0, n - 1); n must be at least 1.
   Stable. Each merge copies its two runs to heap buffers it frees. */
void merge_sort(int* a, size_t lo, size_t hi);

/* Sort a[lo..hi] into ascending order, in place. Same range rule. */
void quick_sort(int* a, size_t lo, size_t hi);

Four public functions. merge and partition are static in sort.c and appear nowhere in the header. The two sorts call themselves directly.
