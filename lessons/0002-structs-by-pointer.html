Structs by Pointer

Dot on the thing, arrow on the pointer, and a loop that walks an array by moving the pointer until it meets the end.

About 20 minutes Where: WSL, exercises/02-rects/ Mission · Cheat sheet · Lesson 1
Your win today. A struct declared once in a header, three functions that reach into it through a pointer (two that only read, one that writes), a loop written with p < end instead of i < n, and two more bug reports read well enough to fix from the report alone: one from the sanitizer, one from the compiler.

The struct goes in the header

A struct is a type you declare, and both files need the same declaration, so it lives in the header next to the prototypes. This is the whole header for today; you will write the other two files from memory.

rect.h

#ifndef RECT_H
#define RECT_H

#include <stddef.h>   /* size_t */

/* An axis-aligned rectangle: bottom-left corner and size, in whole units. */
struct rect {
    int x, y;
    int w, h;
};

/* Area of r. */
int rect_area(const struct rect *r);

/* Move r by dx, dy, in place. */
void rect_move(struct rect *r, int dx, int dy);

/* The rectangle with the largest area among the n at rs. n must be at least 1.
   Returns a pointer into the caller's array, not a copy. */
const struct rect *rect_largest(const struct rect *rs, size_t n);

#endif

The type's full name is the two words struct rect; rect on its own is only the tag and names nothing.A typedef can shorten the two words to one. This course holds off until lesson 7, where typedef struct stack stack; in a header is what makes an opaque type: clients see the name and never the members. On a struct value you reach a member with a dot, s.w, the operator Beej says C's descendants “stole” from it*.

Arrow on a pointer. Every function above takes a pointer to a rect, and through a pointer the member is r->w. It is exactly (*r).w, dereference then dot, with the parentheses folded into one operator*. Beej: “The arrow operator helps refer to fields in pointers to structs”*. The rule is small enough to say in a breath: dot on a struct, arrow on a pointer to one. Get it wrong and the build stops; gcc 13 even names the fix.

Why a pointer at all. Beej gives two cases for passing a pointer to a struct instead of the struct: “You need the function to be able to make changes to the struct that was passed in, and have those changes show in the caller”, and the struct “is somewhat large and it's more expensive to copy that onto the stack than it is to just copy a pointer”*. This course adds a third: from lesson 7 on, every stack, list and tree is a struct that lives on the heap and is only ever touched through a pointer. So rect_move takes struct rect * because it writes, and rect_area takes const struct rect * because it only reads. Same const promise as lesson 1, now made about a struct.To hand a function the address of one element of an array, write &rs[i]. It is the same pointer as rs + i; the second spelling is explained below. Beej's chapter 5 covers the & and * operators if you want the slow version*.

Returning a pointer into the caller's array. rect_largest hands back an address inside rs, not a copy. Two consequences the comment in the header states: the caller must never free that result on its own, and must not use it after freeing rs. Every find and search in lessons 8 to 10 has this shape.

An array becomes a pointer the moment you pass it

The precise rule: an expression of array type, “when used in any context other than as the operand of the address-of operator [or] as the operand of sizeof … undergoes an implicit conversion to the pointer to its first element”*. Beej's version: “Just referring to the array name in isolation is the same as getting a pointer to the first element of the array!”* So inside rect_largest, rs is a pointer and nothing else, and the length has to travel separately, which you already did in lesson 1 with size_t n.

The two exceptions in that rule are exactly where people get bitten, so here is what sizeof measures, as printed on this machine (64-bit WSL, gcc 13):

ExpressionBytesBecause
sizeof(struct rect)16Four ints of four bytes. Parentheses are required around a type name.Add a fifth member char tag; and the answer becomes 20, not 17: the compiler pads the struct so that an array of them keeps every int aligned*. CS107 teaches the rule in its memory weeks. For now, never compute a struct's size by hand; ask sizeof.
sizeof corners, where struct rect corners[4]; is a local array64The whole array, 4 × 16. This is the sizeof exception to decay.

sizeof corners / sizeof corners[0]4The element count, but only in the scope that declared the array.

Two habits fall out of the table. First, size what you point at: malloc(N * sizeof *rs), never sizeof rs. The wrong one is legal C, compiles without a word, and is today's first planted bug. Second, the element-count trick is local. Beej: “This trick only works in the scope in which the array was defined. If you pass the array to a function, it doesn't work”*; on a pointer it “would simply divide the number of bytes in a pointer type by the number of bytes in the pointed type”*, which for a rect is 8 ÷ 16, that is, zero.

Walk the array by moving the pointer

You know the index loop. Today's loop has no index at all:

const struct rect *end = rs + n;                 /* one past the last rect */
for (const struct rect *p = rs; p < end; p++) {
    /* p->w, p->h ... */
}

p + 1 is the next rect, not the next byte. Beej, on an int pointer: “C knows that p is a pointer to an int. So it knows the sizeof an int and it knows to skip that many bytes to get to the next int after the first one!”* For a rect pointer, p++ moves 16 bytes. Indexing is the same arithmetic in different clothes: “a[b] == *(a + b)”, and the two “can be used interchangeably”*. That is why &rs[i] and rs + i are one pointer.

end is a pointer to a rect that does not exist. Computing it and comparing against it is defined; pointer arithmetic is “defined only if both the original pointer and the result pointer are pointing at elements of the same array or one past the end of that array”*. Reading end->w is not, and the sanitizer will show you what that looks like if you take the optional step below.The same rule outlaws p - 1 when p is the first element: there is no “one before the beginning”. Walk forwards.

Subtract two addresses to get an index back. rect_largest returns an address. The output line wants a position. Subtraction turns one into the other.

rs        rs+1      rs+2      rs+3      rs+4       addresses, 16 bytes apart
+---------+---------+---------+---------+---------+
| rect 0  | rect 1  | rect 2  | rect 3  | rect 4  |
+---------+---------+---------+---------+---------+
                    ^
                    big

rs + 2 is the address of rect 2. big holds that address. So big - rs is 2. C does not give you the byte distance, 32. It divides by the size of a rect and gives you the number of rects between the two addresses*. That number is the index. It is rs + 2 run backwards.

The result is an integer with its own type name, ptrdiff_t. It is the signed cousin of size_t. printf needs the matching letter for it, the way it needs %zu for size_t. Write %td.

Why learn this when i < n works? Because a linked list has no i. From lesson 8 on, the only way to walk anything is to move a pointer until it hits a stop value. Learn the shape here, on an array, where you can still check it against the index version.

Reading the report

Same three lines as lesson 1: the kind, frame #0, and the region sentence. Here is the shape the first planted bug produces, abridged; your addresses and line numbers will differ.

==117889==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x504000000038 ...
WRITE of size 4 at 0x504000000038 thread T0
    #0 0x5fa906939580 in main main.c:12
    ...
0x504000000038 is located 0 bytes after 40-byte region [0x504000000010,0x504000000038)
allocated by thread T0 here:
    #0 ... in malloc ...
    #1 ... in main main.c:8
LineRead it as
WRITE of size 4A four-byte store went out of bounds: one int member. Lesson 1's was a READ; the fill loop makes this one a write.
main main.c:12The line in the fill loop that stored it. Not the bug, just where it surfaced.
“0 bytes after 40-byte region”The whole diagnosis is in the number. Five rects need 80 bytes. Forty is 5 × 8: five pointers' worth. Something measured the pointer instead of the rect. The first store to spill is rect 2's third member, at byte 40.
“allocated by … main.c:8”The malloc to fix.

Note what did not happen: no warning. sizeof rs is a perfectly legal 8, and gcc cannot know you meant the rect. Only the run catches it, and only because the block was too small for the loop that followed. That is why the habit is sizeof *rs, not the checker.

The second planted bug never reaches the sanitizer. The compiler stops the build and, since gcc 13, names the fix:

rect.c: In function ‘rect_area’:
rect.c:4:13: error: ‘r’ is a pointer; did you mean to use ‘->’?
    4 |     return r.w * r.h;
      |             ^
      |             ->
rect.c:5:1: warning: control reaches end of non-void function [-Wreturn-type]

Read the first error and stop there. The warnings after it are consequences of the compiler giving up on that line, and vanish once it is fixed. Fix, rebuild, read again from the top. The cheat sheet lists the other messages this material produces, including the one for an arrow on a struct.

If you took the optional step, the report changes shape in two ways worth noticing:

READ of size 4 at 0x5070000000e8 thread T0
    #0 ... in rect_area rect.c:4
    #1 ... in rect_largest rect.c:16
    #2 ... in main main.c:18
0x5070000000e8 is located 8 bytes after 80-byte region

Frame #0 is where the read happened and frame #1 is who handed it the bad pointer: the loop, which let p reach end and then called rect_area(end). The region is 80 bytes, so the allocation is right this time. And “8 bytes after” because rect_area read end->w, and w sits 8 bytes into a rect, after x and y. The sixth rect does not exist; the pointer to it is legal right up until you look through it.
