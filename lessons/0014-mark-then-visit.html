Lesson 14 · DSA in C

Mark, Then Visit

A graph is an array of linked lists. Breadth-first search walks it with lesson 11's queue, depth-first search walks it with the C stack, and both finish for one reason: a vertex is marked the moment it is found, not the moment it is visited.

About 45 minutes Where: WSL, exercises/14-graph/ Mission · Cheat sheet · Lesson 13
Your win today. Ship graph_t as an opaque ADT: adjacency lists built by front insertion, a breadth-first search that borrows your own queue module from lesson 11, a recursive depth-first search, and connected components. With that, every structure on the mission's success list exists in your repo.

Six edges, twelve nodes

Create a graph with 8 vertices, numbered 0 to 7. Add the edges 0-1, 0-2, 1-3, 2-3, 3-4, 5-6 in that order. Vertex 7 gets no edge. Afterwards the memory looks like this:

main's stack     heap
g ──────────▶ struct graph { n 8, adj ──▶ 0x100 }             16 bytes

0x100  adj[0] ──▶ [2|·]──▶[1|NULL]          adj[4] ──▶ [3|NULL]
       adj[1] ──▶ [3|·]──▶[0|NULL]          adj[5] ──▶ [6|NULL]
       adj[2] ──▶ [3|·]──▶[0|NULL]          adj[6] ──▶ [5|NULL]
       adj[3] ──▶ [4|·]──▶[2|·]──▶[1|NULL]   adj[7]     NULL
       (the array: 8 slots of 8 bytes)      each [to|next] box: one 16-byte heap block

Count the heap blocks: one struct graph, one array of 8 pointers, and twelve edge nodes. Twelve, not six. An undirected edge 0-1 is stored twice: a node holding 1 in 0's list and a node holding 0 in 1's list. The list hanging off adj[u] is u's adjacency list: the vertices that share an edge with u. Sedgewick and Wayne call the whole shape the adjacency-lists representation, “a vertex-indexed array of lists of the vertices connected by an edge to each vertex”*, and their Graph.java states its space as proportional to E + V*: one slot per vertex, two nodes per edge.

One edge node is 16 bytes on your machine: a 4-byte int, 4 bytes of padding, an 8-byte pointer. struct graph is also 16: a size_t and a pointer. The experiments later name a “32-byte region”. That is neither of these. It is main's order array, eight ints.

In C both structs are private to graph.c. The header says only typedef struct graph graph_t;, as the stack, list, queue, tree and hashmap did. The node type is spelled struct edge with no typedef, like lesson 11's struct node; lesson 10's typedef struct node node_t; names the same kind of private struct and is equally fine:

struct edge {
    int to;                /* the neighbour at the other end */
    struct edge* next;
};

struct graph {
    size_t n;              /* vertices are 0 .. n-1 */
    struct edge** adj;     /* adj[u] is the head of u's list, NULL when u has no edge */
};

Ownership runs top down. main owns the struct graph through g. The struct owns the array; graph_new gets it from calloc, which “initializes all bytes in the allocated storage to zero”*, so every list starts as NULL without a loop. Each slot adj[u] owns the nodes of u's list. graph_free walks all n lists with lesson 11's saved-next walk, frees the array, then frees the struct: fourteen frees for fourteen blocks.

Add an edge: front insert, twice

Watch adj[3] as the edges that touch 3 arrive:

after 1-3     adj[3] ──▶ [1|NULL]
after 2-3     adj[3] ──▶ [2|·]──▶[1|NULL]
after 3-4     adj[3] ──▶ [4|·]──▶[2|·]──▶[1|NULL]

Each arrival is two pointer writes on a slot: e->next = g->adj[u]; g->adj[u] = e;. The slot adj[u] has type struct edge*, exactly lesson 10's head. Nothing walks the list. The newest neighbour is always first, so a list reads in reverse insertion order: 3's list prints 4 2 1, not 1 2 4. Every expected line in this lesson depends on that order. algs4's Graph has the same shape: addEdge does adj[v].add(w); adj[w].add(v);*, and Bag.add links the new node in front of the old first node*. Skiena's C version comments the same line “insert at head of list”, then calls itself once more with the ends swapped*.

int graph_add_edge(graph_t* g, int u, int v) {
    if (!is_vertex(g, u) || !is_vertex(g, v)) {
        return 0;
    }
    struct edge* uv = malloc(sizeof *uv);      /* allocate both before linking either */
    struct edge* vu = malloc(sizeof *vu);
    if (uv == NULL || vu == NULL) {
        free(uv);                              /* free(NULL) is allowed */
        free(vu);
        return 0;                              /* graph unchanged */
    }
    uv->to = v;
    uv->next = g->adj[u];                      /* front insert: two pointer writes */
    g->adj[u] = uv;
    vu->to = u;
    vu->next = g->adj[v];
    g->adj[v] = vu;
    return 1;
}

Both nodes are allocated before either is linked. If the second malloc fails, the first node is freed and the graph is exactly as it was: the “unchanged on 0” contract from lessons 4, 9 and 11. is_vertex is a two-line static helper: v >= 0 && (size_t)v < g->n. Vertex ids are int because the queue carries ints; the cast is the one place the two types meet.

Breadth-first: mark when enqueued

Breadth-first search from 0 visits 0, then every vertex one edge away, then two edges away, and so on. The queue holds vertices that have been found but whose lists have not been read yet. marked is an array of eight ints from calloc, all 0. “Visit” means: dequeue and append to order[]. Trace it on the graph, reading each list in its stored order:

Five visits, five enqueues, five dequeues. Sedgewick and Wayne state the loop body in one sentence: “Put onto the queue all unmarked vertices that are adjacent to v and mark them”*. The mark and the enqueue happen together, at step 3 of the table, not at step 4. Their BreadthFirstPaths.java has the two lines side by side: marked[w] = true; queue.enqueue(w);*.

Now move the mark to the other side, a natural mistake: mark a vertex when you visit it, right after the dequeue. Same graph, same lists:

At step 3, vertex 1 reads its list while 3 is sitting in the queue unmarked, so 3 is enqueued a second time. Every duplicate dequeue is one extra write into order[], and each one reads its list again and can enqueue further duplicates: 4 goes in twice because 3 came out twice. Seven writes for a component of five vertices, and graph_bfs returns 7. On this graph 7 fits inside main's block of 8 ints, so nothing crashes and the wrong answer prints. Add one more edge, 1-2, and the same code writes nine ints into eight slots; AddressSanitizer stops it. You will do both in the experiments.

The rule, and the title: a mark means “already found: in the queue or out of it”. It never means “already visited”. Mark when you enqueue, visit when you dequeue.

There is a second correct form: leave the mark on the dequeue side, but skip any vertex that is already marked when it comes out. Aspnes describes search that way, as a bucket of edges where an edge whose far end is already in the tree is thrown away when it is popped*. It is correct, and its queue can grow to one entry per edge instead of one per vertex. Every implementation this lesson cites uses the form above. The bug in experiment 1 is the dequeue-side mark without the skip. 
size_t graph_bfs(const graph_t* g, int start, int* order) {
    if (!is_vertex(g, start)) {
        return 0;
    }
    int* marked = calloc(g->n, sizeof *marked);       /* all 0: nothing found yet */
    if (marked == NULL) {
        return 0;
    }
    queue_t* q = queue_new();                          /* lesson 11, unchanged */
    if (q == NULL) {
        free(marked);
        return 0;
    }
    size_t count = 0;
    marked[start] = 1;                                 /* mark when enqueued */
    int ok = queue_enqueue(q, start);
    int v;
    while (ok && queue_dequeue(q, &v)) {
        order[count++] = v;                            /* visit when dequeued */
        for (const struct edge* e = g->adj[v]; ok && e != NULL; e = e->next) {
            if (!marked[e->to]) {
                marked[e->to] = 1;                     /* mark when enqueued */
                ok = queue_enqueue(q, e->to);
            }
        }
    }
    queue_free(q);
    free(marked);
    return count;
}

Three heap blocks take part, and three different owners. marked is created by graph_bfs and freed by graph_bfs before it returns. The queue is created by queue_new inside graph_bfs and freed by queue_free before it returns; the graph never stores it. The queue is a borrowed tool for the length of one call, and lesson 11's header is all graph.c knows about it. order belongs to the caller, who promised room for n ints.

queue_enqueue returns 0 when its malloc fails. The ok flag stops both loops, and the two frees still run, so the function returns a partial count and leaks nothing. An early return is fine too, as long as it frees both blocks first. Two exits, both clean, is the habit that matters.

Depth-first: mark on entry, recurse on the C stack

Depth-first search takes the first unmarked neighbour and goes deeper before it looks at the second. No queue: the C stack remembers where to come back to. From 0 on the same graph, reading each list in stored order:

dfs_visit(0)     mark 0, order: 0          list 2 1.   2 unmarked:
  dfs_visit(2)     mark 2, order: 0 2        list 3 0.   3 unmarked:
    dfs_visit(3)     mark 3, order: 0 2 3      list 4 2 1. 4 unmarked:
      dfs_visit(4)     mark 4, order: 0 2 3 4    list 3: marked. return
    2 marked, 1 marked. return
  0 marked. return
                                              1 unmarked:
  dfs_visit(1)     mark 1, order: 0 2 3 4 1  list 3 0: both marked. return

Four frames are alive at the deepest point, one each for 0, 2, 3 and 4. Each frame holds five arguments and no node pointer, unlike lesson 12: a vertex is a number, and the number is its position in adj. The visit count travels as size_t* count because every frame appends to the same order[] and must see the same counter. A size_t copy would die with its frame, the same way lesson 12's insert_at on a copy lost its node. Sedgewick and Wayne describe the visit in two lines: “Mark it as having been visited. Visit (recursively) all the vertices that are adjacent to it and that have not yet been marked”*, and marked[v] = true is the first line of their dfs*:

static void dfs_visit(const graph_t* g, int v, int* marked, int* order, size_t* count) {
    marked[v] = 1;                             /* mark on entry, before the loop */
    order[(*count)++] = v;
    for (const struct edge* e = g->adj[v]; e != NULL; e = e->next) {
        if (!marked[e->to]) {
            dfs_visit(g, e->to, marked, order, count);
        }
    }
}

size_t graph_dfs(const graph_t* g, int start, int* order) {
    /* is_vertex check, calloc marked, count = 0 */
    dfs_visit(g, start, marked, order, &count);
    free(marked);
    return count;
}

The mark is the first line. Move it below the loop, as if it were a post-order step like lesson 12's free_nodes, and the edge 3-4 becomes a loop: 3 enters 4, 4 finds 3 unmarked and enters 3, 3 finds 4 unmarked and enters 4. No frame ever reaches its mark, so no base case ever fires. The C stack fills and AddressSanitizer reports stack-overflow under a column of dfs_visit frames. With the mark on entry, the deepest possible stack is one frame per vertex: a path 0-1-2-... started at 0 puts n frames on the stack, and the frames are small, so the default 8 MB stack holds anything this course builds.

Components: the label is the mark

A connected component is a set of vertices with a path between every two of them. Sedgewick and Wayne: a graph that is not connected “consists of a set of connected components, which are maximal connected subgraphs”*. This graph has three: {0, 1, 2, 3, 4}, {5, 6} and {7}. One loop finds them. For v from 0 to n - 1: if v has no label yet, run a depth-first walk from v and give everything it reaches the next id. CC.java does exactly this with a marked[] and an id[] side by side, and bumps count after each walk*. Skiena's connected.c runs his bfs from every vertex not yet discovered*. Here the label array is the mark: component[v] == -1 means not yet found.

static void label_visit(const graph_t* g, int v, int* component, int id) {
    component[v] = id;                         /* the label is the mark */
    for (const struct edge* e = g->adj[v]; e != NULL; e = e->next) {
        if (component[e->to] == -1) {
            label_visit(g, e->to, component, id);
        }
    }
}

/* graph_components: fill component[] with -1; then for each v with component[v] == -1,
   label_visit(g, v, component, id) and id++; return id. */

Fill the array with -1 first. The first component gets id 0, so a zero from calloc would read as “already in component 0” and the loop would label nothing. The result for this graph is 0 0 0 0 0 1 1 2 and a count of 3. Vertex 7 has an empty list, so its walk marks one vertex and returns.

Count the work in any of the three walks: each vertex is entered once, because the mark stops a second entry, and each list is read once, when its vertex is entered. That is proportional to V + E. algs4 states it for both: BFS “takes time proportional to V + E in the worst case”, and DFS “marks all the vertices connected to a given source in time proportional to the sum of their degrees”*. Without the mark the same code walks a cycle forever. That is the whole lesson in one sentence.

The interface

graph.h

#pragma once

#include <stddef.h>

typedef struct graph graph_t;

/* Create a graph with vertices 0 .. vertex_count-1 and no edges. NULL on allocation failure. */
graph_t* graph_new(size_t vertex_count);

/* Free every edge node, the array of lists, then the graph. NULL is fine. */
void graph_free(graph_t* g);

/* Add the undirected edge u-v: v joins u's list and u joins v's list.
   Returns 1, or 0 on a bad vertex or allocation failure. On 0 the graph is unchanged. */
int graph_add_edge(graph_t* g, int u, int v);

/* Number of vertices. */
size_t graph_vertex_count(const graph_t* g);

/* Number of neighbours in v's list. 0 for a bad vertex. */
size_t graph_degree(const graph_t* g, int v);

/* One line per vertex: "v:" then each neighbour preceded by one space, then a newline. */
void graph_print(const graph_t* g);

/* Breadth-first from start. Writes the visit order into order[], which must hold
   at least graph_vertex_count(g) ints. Returns how many vertices were visited. */
size_t graph_bfs(const graph_t* g, int start, int* order);

/* Depth-first from start, recursive. Same contract as graph_bfs. */
size_t graph_dfs(const graph_t* g, int start, int* order);

/* Label every vertex: component[v] = id of its connected component, ids 0, 1, ...
   in order of the smallest vertex in each. Returns the number of components. */
size_t graph_components(const graph_t* g, int* component);

One function changes the graph and takes graph_t*. Six only read it and take const graph_t*, including the three walks: they write their own arrays, never the graph. queue.h is included by graph.c only. main.c never sees a queue.

Read next

Everything here is C or language-free theory. Read in this order; the first two items are short source files, not chapters.

  1. The same graph in Skiena's C. Steven Skiena, The Algorithm Design Manual, 2nd ed., the author's program files: graph.h, graph.c, bfs-dfs.c and connected.c. His edgenode is your struct edge with a weight added, and edges[] is your adj. Read insert_edge first: p->next = g->edges[x]; g->edges[x] = p; under the comment “insert at head of list”, then one call to itself with x and y swapped for the undirected case. Then bfs: enqueue(&q,y); discovered[y] = TRUE; are adjacent lines, the rule of this lesson; processed[v] is a second mark set on dequeue that you did not need. Then dfs: discovered[v] = TRUE before the loop. connected_components is your graph_components with bfs in place of the recursive helper. Read for the shape, not the style: vertices are numbered from 1, the graph is one fixed-size struct with MAXV of 100, discovered and processed are global arrays instead of a heap block owned by the search, the queue in queue.c is a fixed array of 1000 ints, and the functions are written in the pre-C99 form with no return type. gcc 13 still builds the four files under your flags, but with a screen of warnings: return type defaults to ‘int’, an implicit printf, control reaches end of non-void function. The algorithm underneath is the one you just wrote.

  2. A search in C where the parent is the mark. James Aspnes, Notes on Data Structures and Programming Techniques (Yale CPSC 223), section 5.14 Graphs: read 5.14.4, Representations of graphs and 5.14.5.1, Implementation of depth-first and breadth-first search, which is the file search.c. Each vertex keeps a parent, and VERTEX_NULL in that slot means unvisited, so one array does the job of your marked and of your component label; the root's parent is itself. His dfsHelper tests the slot on entry and writes it before its loop, under the comment “this uses a recursive algorithm and will not work on large graphs!”: your stack-depth limit, in someone else's words. His bfs writes g->v[nbr].parent = current; q[tail++] = nbr;, mark then enqueue, and its queue is a plain array of n ints with a head and a tail index, which is enough because a vertex is enqueued at most once. Neighbours there are a VERTEX_NULL-terminated array rather than a list. Skip graphForeach in his graph.h under 5.14.4: it takes a function pointer, which is CS107 lecture 9 material.

  3. Theory, no code. Pseudocode with three colours where you have one mark: white is unmarked, grey and black are both marked. The DFS pseudocode paints u grey as its first line, and the running-time argument rests on it: “DFSVisit is called exactly once for each vertex ... since the vertex on which DFSVisit is invoked must be white, and the first thing DFSVisit does is paint that vertex grey.” The BFS argument is the same sentence for the queue: “we only add white vertices to the queue (and mark them grey when they are added) ... it follows that we only add a vertex to the queue at most once.” Both put the cost at Θ(m + n); her m and n are algs4's E and V.
