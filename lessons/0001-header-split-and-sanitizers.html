Two Files, Two Bugs

A header that promises, a source file that delivers, a client that only sees the promise. Then break it on purpose and read what the sanitizer says.

About 20 minutes Where: WSL, exercises/01-build-loop/ Mission · Cheat sheet
Your win today. A two-file C program written from memory, with a header that hides the implementation, and two memory-bug reports read well enough to fix the bug from the report alone.

Setup · paste once · not something to learn

This is the only tooling in the whole course. CS107 teaches it in week 1, so you do not need to remember any of it. Put this file, named Makefile, in the exercise folder. Then make builds, ./sum runs, make check runs the program under valgrind to look for leaks, and make clean removes the binaries. The ⇥ marks must be real tab characters.

CC     = gcc
CFLAGS = -std=gnu11 -Wall -Wextra -g
SAN    = -fsanitize=address,undefined
SRC    = main.c vec.c

sum: $(SRC) vec.h
⇥$(CC) $(CFLAGS) $(SAN) -o sum $(SRC)

# valgrind cannot run a sanitized binary, so it gets a plain one
sum-plain: $(SRC) vec.h
⇥$(CC) $(CFLAGS) -o sum-plain $(SRC)

.PHONY: check clean
check: sum-plain
⇥valgrind --leak-check=full --error-exitcode=1 ./sum-plain
clean:
⇥rm -f sum sum-plain

What the flags do lives in the cheat sheet, for the day you are curious. The one effect that matters now: ./sum stops loudly on an out-of-bounds or use-after-free the moment it happens, and make check reports anything you forgot to free.

The header is the promise

The CS107 prerequisite asks for “data abstraction” and “well-decomposed, readable code”*. In C the smallest unit of both is a module in two files: a header that states what the module offers, and a .c file that implements it. Any client includes the header and never looks inside the .c. Every stack, list, tree and map in this course is shipped this way.

vec.h

#ifndef VEC_H
#define VEC_H

#include <stddef.h>   /* size_t */

/* Sum of the first n elements of a. a must point to at least n ints. */
int vec_sum(const int *a, size_t n);

#endif

Three things in those lines are worth owning, because you will write them hundreds of times.

The prototype is the contract. Beej: function prototypes go in the .h, definitions go in the .c, and “any file that wants that add() functionality can just #include "bar.h" to get it”*. The comment above it is part of the contract: what the function does, and what the caller must guarantee.

const int *a is a promise about writing. It says: through a, this function will only read. The caller may pass a perfectly ordinary int array; the const binds the function, not the caller*. Make every read-only pointer parameter const; it documents intent and the compiler enforces it.Read pointer declarations right to left: const int *a is “a is a pointer to a const int”. The pointer itself can still be moved; it is the ints that are read-only through it.

size_t is the type for counts and sizes. It is unsigned and as wide as a pointer, which is what malloc, strlen and sizeof all speak. Using int for a length gets you a warning today and a sign bug later. It lives in <stddef.h>.

The #ifndef / #define / #endif wrapper is an include guard. Beej: “The stuff that we're about to do is so common that you should just automatically do it every time you make a header file!”* It makes a second #include of the same header expand to nothing, so nothing is declared twice.Name the guard after the file in capitals, VEC_H. Never start it with an underscore; those names belong to the compiler and library.

Two rules on the other side: the first line of vec.c is #include "vec.h", so the compiler checks your definition against your own promise. And main.c includes vec.h, never vec.c.

Reading the report

This is the skill, not the tool. Off-by-one, use-after-free and leaks are exactly the bugs linked lists and trees produce, and the report is how you will find yours in every later lesson. It looks like a wall of hex; three lines carry the meaning. Here is the shape your first planted bug produces, abridged, with addresses that will differ on your machine.

==87849==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000020 ...
READ of size 4 at 0x502000000020 thread T0
    #0 0x5f30d5e65374 in vec_sum vec.c:5
    #1 0x5f30d5e654f3 in main main.c:11
    ...
0x502000000020 is located 0 bytes after 16-byte region [0x502000000010,0x502000000020)
allocated by thread T0 here:
    #0 ... in malloc ...
    #1 ... in main main.c:7
LineRead it as
The ERROR lineThe kind of bug. heap-buffer-overflow: an index ran off the end of a malloc'd block.
Frame #0 of the first stackWhere the bad access happened: function, file, line. Frame #1 is who called it.
“located 0 bytes after 16-byte region”How far past the block, and how big the block was. 16 bytes is four ints. Zero bytes after it means you read exactly one element too far: the classic <=.
“allocated by … here”The second stack is the malloc that created the block, so you can pair the access with its allocation.

The second planted bug is a leak, and leaks are reported by a different tool. make check runs your program under valgrind, the checker CS107 itself uses*, and at exit it prints:

==112784== 16 bytes in 1 blocks are definitely lost in loss record 1 of 1
==112784==    at 0x4846828: malloc (in /usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so)
==112784==    by 0x10917E: main (main.c:6)
...
==112784==    definitely lost: 16 bytes in 1 blocks

Same discipline: kind (“definitely lost”), size, and the line that allocated the block nobody freed. When everything is freed the summary reads “All heap blocks were freed -- no leaks are possible”.Why not the sanitizer for leaks too? It does try, but at exit it counts a block as “still reachable” if any copy of its address is lying around in stack memory, and an unoptimised build leaves stale copies behind in dead frames. That is why the first attempt at this bug was silent. Valgrind tracks reachability more carefully and calls the block lost. The cheat sheet lists the other headings you will meet later.
