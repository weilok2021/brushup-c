Lesson 9 · DSA in C

Head and Tail

A queue is lesson 8's list with a second pointer at the far end. Two pointers, two invariants, and one dangling-pointer trap when the last node leaves.

About 40 minutes Where: WSL, exercises/09-queue/ Mission · Cheat sheet · Lesson 8
Your win today. Ship a linked queue as an opaque ADT with worst-case constant-time enqueue and dequeue, and see for yourself what AddressSanitizer says when a tail pointer outlives its node. Lesson 12 will use this exact module for breadth-first search, so its interface is general and stays fixed.

Setup · paste once · not something to learn

Put this Makefile in the exercise folder. The ⇥ marks must be real tabs.

CC     = gcc

⇥$(CC) $(CFLAGS) $(SAN) -o queue $(SRC)

⇥rm -f queue queue-plain

Three values, four heap blocks

Enqueue 10, then 20, then 30. Afterwards the memory looks like this:

main's stack frame            heap
-----------------             -------------------------------------------
q: 0x5010 ------------------> 0x5010  struct queue   (24 bytes)
                                      head:  0x5050
                                      tail:  0x5090
                                      count: 3

                              0x5050  struct node    (16 bytes)
                                      value: 10   next: 0x5070
                              0x5070  struct node
                                      value: 20   next: 0x5090
                              0x5090  struct node
                                      value: 30   next: NULL

Every byte here is accounted for. The variable q lives in main's stack frame and holds one address. The queue struct is a heap block of 24 bytes: two pointers of 8 bytes each and a size_t. Each node is a heap block of 16 bytes: a 4-byte int, 4 bytes of padding, and an 8-byte next pointer. The queue struct owns every node. main owns the queue struct, through q, and gives it back with one call to queue_free.

Keep the 16 in mind. AddressSanitizer will describe a node as a “16-byte region” later, and that number tells you which kind of block it is talking about.

The two structs are private to queue.c. The header only says typedef struct queue queue_t;, so main.c can hold a queue_t* and cannot reach inside it. That is the same opaque-struct shape as lessons 7 and 8. Lesson 8 added typedef struct node node_t; inside list.c; this lesson writes the plain struct node spelling. Both name the same private struct, so use whichever you prefer:

struct node {
    int value;
    struct node* next;
};

struct queue {
    struct node* head;   /* oldest node, NULL when empty */
    struct node* tail;   /* newest node, NULL when empty */
    size_t count;
};

Lesson 8's list had only head. Adding at the far end meant walking every node first. The queue adds tail so that the far end is always one pointer away. Sedgewick and Wayne keep the same two references, first and last: “To enqueue() an item, we add it to the end of the list; to dequeue() an item, we remove it from the beginning of the list”*.

Two invariants

A second pointer is a second thing that can be wrong. Two rules must hold between calls, and every function must leave both of them true:

InvariantMeaningWho relies on it
head == NULL exactly when tail == NULLBoth ends agree about emptiness. An empty queue has no node for either to point at.queue_enqueue tests only tail; queue_dequeue tests only head.
tail->next == NULL whenever tail is setThe tail is the real last node. Nothing hangs off it.queue_free stops at the right place; queue_enqueue may link after tail without a walk.

An invariant is a statement about the struct that is true before and after every public call. Inside a call it may be false for a few lines. Both planted bugs in this lesson break the first invariant, in opposite directions, and each one shows up as a different sanitizer report.

Enqueue: two cases

Enqueue always allocates one node, fills it, and makes it the new tail. The only question is what the old tail was:

empty queue          enqueue 10             non-empty queue        enqueue 20
head: NULL           head: 0x5050           head: 0x5050           head: 0x5050
tail: NULL           tail: 0x5050           tail: 0x5050           tail: 0x5070
                     [10 | NULL]            [10 | NULL]            [10 | 0x5070] [20 | NULL]
                     ^ both ends                                     ^ old tail's next written

On an empty queue there is no old tail to link after, so head must be set to the new node too. Miss that and head stays NULL forever: tail and count say the queue has nodes, head says it is empty, and the first invariant is broken.

int queue_enqueue(queue_t* q, int v) {
    struct node* n = malloc(sizeof *n);
    if (n == NULL) {
        return 0;
    }
    n->value = v;
    n->next = NULL;                  /* second invariant, kept by construction */
    if (q->tail == NULL) {
        q->head = n;                 /* empty: the new node is both ends */
    } else {
        q->tail->next = n;           /* link after the old tail */
    }
    q->tail = n;
    q->count++;
    return 1;
}

Allocation failure leaves the queue exactly as it was and returns 0. That is the same “unchanged on failure” contract as lesson 4's word_replace and lesson 7's push.

Dequeue: two cases, and the trap

Dequeue copies the head's value out, unlinks the head, frees it, and returns 1. The trap is the moment the queue goes from one node to none:

one node             after head = old->next   after free(old)
head: 0x5050         head: NULL               head: NULL
tail: 0x5050         tail: 0x5050             tail: 0x5050   <-- points at a freed block
[10 | NULL]          [10 | NULL]              (16 bytes, no longer yours)

tail still holds 0x5050. The node at 0x5050 has been freed. tail is a dangling pointer, and the first invariant is broken again: head is NULL and tail is not. Nothing crashes yet. The next queue_enqueue sees tail != NULL, takes the non-empty branch, and executes q->tail->next = n: an 8-byte write into a freed block. AddressSanitizer stops the program there. Without the sanitizer, the write lands in whatever malloc has since handed out, and the queue silently loses nodes.

Beej, 12.1: “It's undefined behavior to use a memory region after you free() it.” Manual Memory Allocation. cppreference states the same rule for free: the behaviour is undefined if an access is made through the pointer after free returns.

The fix is one test. When the new head is NULL, the queue is empty, so tail must become NULL too:

int queue_dequeue(queue_t* q, int* out) {
    if (q->head == NULL) {
        return 0;
    }
    struct node* old = q->head;
    *out = old->value;
    q->head = old->next;
    if (q->head == NULL) {
        q->tail = NULL;              /* last node gone: tail must not dangle */
    }
    free(old);
    q->count--;
    return 1;
}

The Java version in algs4 has the same line, if (isEmpty()) last = null;, with the comment “to avoid loitering”*. In Java the cost of forgetting it is a node kept alive by the garbage collector. In C the node is already gone, and the cost is a write into memory you do not own. Same line, much higher stakes.

The value goes out through int* out, and the function returns 1 or 0 to say whether anything was removed. That keeps -1 or 0 free to be real queue values. It also means no pointer into a node ever leaves queue.c, so no caller can hold a node after it is freed. Lesson 10 will return borrowed pointers and pay for it with one deliberate use-after-free.

Peek, count, empty, free

queue_peek is dequeue without the unlink: copy head->value into *out, return 1, or return 0 when head is NULL. queue_count returns the counter. queue_is_empty returns head == NULL. All three take const queue_t* because they only read.

queue_free is lesson 8's saved-next walk. Read cur->next before free(cur), because after the free the node's bytes are not yours to read:

void queue_free(queue_t* q) {
    if (q == NULL) {
        return;
    }
    struct node* cur = q->head;
    while (cur != NULL) {
        struct node* next = cur->next;   /* save before free */
        free(cur);
        cur = next;
    }
    free(q);
}

The walk starts from head. If head was never set (the enqueue bug above), the walk frees nothing, free(q) drops the only remaining route to the nodes, and Valgrind reports them as definitely lost.

Constant time, worst case

Count the work in queue_enqueue: one malloc, two member writes on the new node, one or two pointer writes on the queue, one increment. queue_dequeue is one copy, one or two pointer writes, one free, one decrement. Neither touches any node other than the one arriving or leaving, so neither depends on how many nodes are queued. For the linked implementation, Sedgewick and Wayne state that “the enqueue, dequeue, peek, size, and is-empty operations all take constant time in the worst case”*.

Compare lesson 7's array stack. Most pushes were one store, but the push that filled the array had to copy every element into a bigger block. The cost was constant only on average over many pushes, which is what “amortised” means. algs4's resizing-array stack works the same way: “We double the size of the array in push() if it is full”*. The linked queue has no such push. Every single call costs the same. That is why it is the right queue for lesson 12's breadth-first search, where enqueue and dequeue run once per vertex and once per edge.

The interface

queue.h

#pragma once

#include <stddef.h>

typedef struct queue queue_t;

/* Create an empty queue. Returns the new owner handle, or NULL on failure. */
queue_t* queue_new(void);

/* Free every node still in the queue, then the queue itself. NULL is fine. */
void queue_free(queue_t* q);

/* Add v at the tail. Returns 1 on success, 0 if a node could not be allocated. */
int queue_enqueue(queue_t* q, int v);

/* Remove the head value into *out. Returns 1 if a value was removed, 0 if empty. */
int queue_dequeue(queue_t* q, int* out);

/* Copy the head value into *out without removing it. Returns 1, or 0 if empty. */
int queue_peek(const queue_t* q, int* out);

/* Number of values currently in the queue. */
size_t queue_count(const queue_t* q);

/* Returns 1 if the queue holds no values, else 0. */
int queue_is_empty(const queue_t* q);

Two functions write the queue and take queue_t*. Three only read and take const queue_t*. Nothing in this header mentions struct node: the node is an implementation detail, and lesson 12 will not need to know it exists.

Reading the two reports

Experiment 1, the dangling tail. Dequeue frees the last node but leaves tail pointing at it. The next enqueue writes through it:

ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000058
WRITE of size 8 at 0x502000000058 thread T0
    #0 ... in queue_enqueue queue.c:...
    #1 ... in main main.c:...
0x502000000058 is located 8 bytes inside of 16-byte region
freed by thread T0 here:
    #0 ... in free
    #1 ... in queue_dequeue queue.c:...
    #2 ... in drain main.c:...
previously allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in queue_enqueue queue.c:...

Read it as a timeline, bottom to top. The block was allocated by an enqueue (the node for 30). It was freed by a dequeue inside drain. Then a later enqueue wrote 8 bytes at offset 8 inside it. Offset 8 in a 16-byte node is the next member, so the write is q->tail->next = n. The pointer that carried the stale address across those three events is tail. Valgrind on the plain build says the same thing as “Invalid write of size 8 … Address is 8 bytes inside a block of size 16 free'd”, and adds that the new node is definitely lost, because the only link to it was written into a dead block.

Experiment 2, the head that was never set. No bad access happens, so the run completes. The output itself is the evidence:

count: 3
first:
empty: yes
count: 5
second:
empty: yes

No peek line, because peek reads head and head is NULL. count says 3 and 5, empty says yes: the counter and the pointers disagree, which is the first invariant broken. Then the leak report. LeakSanitizer catches this one even at -O0, because no stack copy of the first node's address survives to the end of main:

ERROR: LeakSanitizer: detected memory leaks
Direct leak of 16 byte(s) in 1 object(s) allocated from:
    #1 ... in queue_enqueue queue.c:...
Indirect leak of 32 byte(s) in 2 object(s) ...
Indirect leak of 32 byte(s) in 2 object(s) ...
SUMMARY: AddressSanitizer: 80 byte(s) leaked in 5 allocation(s).

make check agrees: “80 (16 direct, 64 indirect) bytes in 1 blocks are definitely lost”. One direct loss is the first node, which nothing points at once free(q) runs. The other four are indirect: they are reachable only through the lost one. Five 16-byte nodes, 80 bytes. When a leak report shows one direct block and a chain of indirect ones, look for a head pointer that was never set or was overwritten.
