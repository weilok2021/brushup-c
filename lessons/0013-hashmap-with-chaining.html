Lesson 13 · Hashmap with chaining · DSA in C

Hash, Then Chain

A hashmap is an array of lesson 10's lists. A string picks the list; strcmp picks the node. When the lists get long, a bigger array is allocated and every node is moved into it without copying a single key.

About 45 minutes Where: WSL, exercises/13-hashmap/ Mission · Cheat sheet · Lesson 12
Your win today. Ship hashmap_t, a string-keyed map of ints, as an opaque ADT: djb2 over the key, one chain per bucket, a map that owns a copy of every key, a resize that relinks nodes instead of copying them, and a test program in which you watch the bucket array double from 4 to 8.

Six keys, eight buckets, three kinds of block

Put six fruit names with a number each: pear 3, fig 12, banana 7, apple 5, kiwi 9, mango 4. When the test program is done inserting, memory looks like this. One variable in main's frame; everything else on the heap:

main's frame     heap
m ──────────▶ struct hashmap (24 bytes) { buckets ──▶ 0x300, capacity 8, count 6 }

0x300  the bucket array: 8 slots of 8 bytes, 64 bytes, one struct node* per slot
       [0] NULL   [1] 0x160   [2] NULL   [3] 0x0d0   [4] NULL   [5] 0x0a0   [6] 0x100   [7] 0x190

       node (24 bytes)                              key copy (strlen + 1 bytes)
0x160  [ key 0x400 | value 9  | next NULL  ]        0x400  "kiwi\0"     5 bytes
0x0d0  [ key 0x410 | value 12 | next NULL  ]        0x410  "fig\0"      4 bytes
0x0a0  [ key 0x420 | value 3  | next NULL  ]        0x420  "pear\0"     5 bytes
0x100  [ key 0x430 | value 7  | next NULL  ]        0x430  "banana\0"   7 bytes
0x190  [ key 0x440 | value 4  | next 0x130 ]        0x440  "mango\0"    6 bytes
0x130  [ key 0x450 | value 5  | next NULL  ]        0x450  "apple\0"    6 bytes

Three kinds of heap block. The bucket array is one block of capacity pointers, every one either NULL or the head of a chain. A node is one block of 24 bytes: a pointer to the key, the int value, 4 bytes of padding, and the pointer to the next node in the same chain. A key copy is the block strdup made: the characters plus the terminating zero. Bucket 7 holds a chain of two nodes; every other used bucket holds one.

The 24 will show up in AddressSanitizer's report in experiment 3 as a “24-byte region”, and the offset 8 inside it is the value member: 8 bytes of key pointer come first. Lesson 12's node was also 24 bytes, laid out differently: there the 4-byte key came first.

Ownership has four levels and reads top down. main owns the struct hashmap through m. The struct owns the bucket array. Each slot in the array owns the chain it heads, exactly as l->head owned lesson 10's list. Each node owns the node after it and owns its key copy. Fourteen blocks are alive in the picture: one struct, one array, six nodes, six key copies. One hashmap_free releases all fourteen.

In C the two structs are private to hashmap.c. The header says only typedef struct hashmap hashmap_t;. The node is spelled struct node as in lessons 11 and 12; lesson 10's typedef struct node node_t; names the same kind of private struct and is equally fine:

struct node {
    char* key;                 /* the map's own copy, made by strdup */
    int value;
    struct node* next;         /* next node in the same bucket's chain */
};

struct hashmap {
    struct node** buckets;     /* capacity slots; each holds a chain head or NULL */
    size_t capacity;           /* number of buckets */
    size_t count;              /* number of keys */
};

struct node** is the type you met in lesson 4: a pointer to the first of a row of pointers. There the row held char*; here it holds struct node*. Nothing else is new about it.

From a string to a bucket

Which slot does "fig" go in? Start from 5381. For each character, multiply by 33 and add the character's code (f is 102, i is 105, g is 103):

start            5381
'f'  5381 × 33 + 102   =    177675
'i'  177675 × 33 + 105 =   5863380
'g'  5863380 × 33 + 103 = 193491643      hash("fig")

193491643 % 4 = 3     bucket 3 of 4
193491643 % 8 = 3     bucket 3 of 8

That number is the hash of the string, and the remainder after dividing by the number of buckets is its bucket index. The same arithmetic for all six keys, plus grape, which the test program looks up and never inserts:

Keyhash (djb2)% 4% 8
pear638557914915
fig19349164333
banana695334350647026
apple21070673464737
kiwi638540453711
mango21072042431137
grape21071390584404

Read the % 4 column: fig, apple and mango all land in bucket 3. Same remainder, three different strings. A bucket therefore holds a chain, and finding a key means hashing to the chain and then walking it with strcmp. Weiss's separate-chaining Find carries the comment “Probably need strcmp!!” at exactly that line, because his keys are int and yours are not*. Comparing pointers would say two equal strings differ; comparing hashes would say apple and mango agree in bucket 7. Only the characters decide.

The function is four lines. It is called djb2, after Dan Bernstein, who posted it to comp.lang.c; the constants 5381 and 33 are his:

/* djb2: start at 5381, then hash = hash * 33 + c for each byte.
   Unsigned on purpose: wraparound is defined, signed overflow is not. */
static unsigned long hash_djb2(const char* s) {
    unsigned long hash = 5381;
    for (; *s != '\0'; s++) {
        hash = hash * 33 + *s;
    }
    return hash;
}

static size_t index_of(const hashmap_t* m, const char* key) {
    return hash_djb2(key) % m->capacity;
}
Ozan Yigit's page keeps Bernstein's original: unsigned long hash = 5381; ... hash = ((hash << 5) + hash) + c; /* hash * 33 + c */, and notes that “the magic of number 33 ... has never been adequately explained”*. Weiss's Hash3 in hashfunc.c is the same shift-and-add shape with an unsigned int accumulator and no 5381 start*. Sedgewick and Wayne hash strings the same way with 31 in place of 33*.

Why unsigned long. Look at pear in the table: 6,385,579,149. That is more than 232, and the running total passes 231 on the fourth character of every four-letter key. In an int that is signed overflow, which C leaves undefined, and UBSan will say so in experiment 1. In an unsigned type the arithmetic wraps modulo 264 by definition, and a hash does not care which bits it lost. index_of is a one-line helper so that every function computes the bucket the same way.

Put: find the chain, copy the key, push

Insert fig 12 into an empty map of 4 buckets. Hash to bucket 3; walk the chain there, which is empty; allocate a node; copy the key; push the node at the head of the chain:

/* Walk one chain. Returns the node holding key, or NULL. */
static struct node* find_in(struct node* head, const char* key) {
    for (struct node* n = head; n != NULL; n = n->next) {
        if (strcmp(n->key, key) == 0) {
            return n;
        }
    }
    return NULL;
}

int hashmap_put(hashmap_t* m, const char* key, int value) {
    size_t i = index_of(m, key);
    struct node* found = find_in(m->buckets[i], key);
    if (found != NULL) {
        found->value = value;                            /* overwrite: no allocation */
        return 1;
    }
    struct node* n = malloc(sizeof *n);
    if (n == NULL) {
        return 0;
    }
    n->key = strdup(key);                                /* the map's own copy */
    if (n->key == NULL) {
        free(n);
        return 0;
    }
    n->value = value;
    n->next = m->buckets[i];                             /* push onto the chain */
    m->buckets[i] = n;
    m->count++;
    if (m->count > m->capacity * 3 / 4) {
        hashmap_grow(m);                                 /* a failed grow loses nothing */
    }
    return 1;
}

The map owns a copy of every key. strdup allocates a fresh heap block and copies the characters into it. The CS107 library guide calls it “equivalent to malloc + strcpy” and warns that it “allocates heap memory secretly, forcing client to know to free”*. Here the client of strdup is hashmap_put, so the map is the owner, and hashmap_remove and hashmap_free are where the copies die. The caller keeps ownership of its own string. It can be a literal, a stack buffer, or a line read from a file that is overwritten a moment later; the map does not care, because it never looks at the caller's bytes again. Lesson 4's word_replace made the same choice for the same reason: a slot that stores a borrowed pointer is not an owner, and experiment 2 shows what happens when the map pretends to be one.

Two smaller points. A put of a key that is already present overwrites the value in place and allocates nothing, so count is unchanged. And the push goes at the head of the chain: n->next takes the old head first, then the slot takes n, the same two lines in the same order as lesson 10's insert.

Load factor: when four buckets are not enough

Suppose the map never grew. Six keys in 4 buckets, using the % 4 column above and pushing at the head:

[0]  NULL
[1]  kiwi ──▶ pear
[2]  banana
[3]  mango ──▶ apple ──▶ fig

6 keys / 4 buckets = 1.5 keys per bucket on average; the longest chain is 3

The ratio 6/4 is the load factor: keys divided by buckets, which is the average chain length. Sedgewick and Wayne: “In a separate-chaining hash table with M lists and N keys, the number of compares (equality tests) for search and insert is proportional to N/M”*. Let N grow with M fixed and every lookup turns into lesson 10's list walk. So the map keeps the ratio bounded by growing the array. The rule this lesson uses:

After adding a key, if count > capacity * 3 / 4, double the bucket array. With 4 buckets the threshold is 3, so the fourth key triggers the first resize. With 8 it is 6; with 16 it is 12.

Trace the test program. After pear, fig, banana: count 3, not more than 3, still 4 buckets. apple goes into bucket 3 in front of fig, count becomes 4, and 4 > 3: grow to 8. Then kiwi and mango arrive into the 8-bucket array: count 6, not more than 6. The output shows the change:

after 3 puts: count 3, capacity 4
after 6 puts: count 6, capacity 8

Three-quarters is a choice, not a law. Sedgewick and Wayne's separate-chaining table starts at 4 buckets like yours, doubles when the average chain reaches 10, and halves when it drops to 2*. Weiss's C version never resizes at all; it picks a prime table size once and lives with it. A lower threshold means shorter chains and more resizes. This lesson uses a low one so that a six-key test shows a resize. Whatever the threshold, the doubling makes the cost amortised in the same way as lesson 9's stack: one put copies pointers for every node, but n puts do about n work in total.

Weiss's InitializeTable rounds the requested size up with NextPrime and has no rehash*; Sedgewick and Wayne describe “modular hashing: we choose the array size M to be prime”*. A prime size helps a weak hash spread. Doubling from 4 gives powers of two instead, and djb2 spreads the six keys well enough in the table above. Both designs are correct; the prime one is a fine change to make once the doubling version works.

Resize moves nodes; it copies nothing

This is the ownership point of the lesson. The resize replaces the bucket array. It does not replace a node, and it does not touch a key copy. Here is the moment apple pushed the count past 3, with the node addresses from the first diagram:

old array, 4 slots                          new array, 8 slots
[0] NULL                                    [0] NULL
[1] 0x0a0 pear                              [1] NULL
[2] 0x100 banana                            [2] NULL
[3] 0x130 apple ──▶ 0x0d0 fig               [3] 0x0d0 fig
                                            [4] NULL
                                            [5] 0x0a0 pear
                                            [6] 0x100 banana
                                            [7] 0x130 apple

four nodes, same four addresses, same four key copies; only the array is new

apple and fig shared bucket 3 of 4 and now sit in buckets 7 and 3 of 8. Each node was unlinked from its old chain and pushed onto its new one. Its key member was read (to compute the new index) and never written. The code:

/* Double the bucket array and relink every existing node into it.
   No node is copied or freed and no key is copied; only the old array is freed.
   Returns 1, or 0 with the map unchanged. */
static int hashmap_grow(hashmap_t* m) {
    size_t new_capacity = m->capacity * 2;
    struct node** bigger = calloc(new_capacity, sizeof *bigger);
    if (bigger == NULL) {
        return 0;
    }
    for (size_t i = 0; i < m->capacity; i++) {
        struct node* n = m->buckets[i];
        while (n != NULL) {
            struct node* next = n->next;                 /* save before relinking */
            size_t j = hash_djb2(n->key) % new_capacity; /* new home */
            n->next = bigger[j];
            bigger[j] = n;
            n = next;
        }
    }
    free(m->buckets);                                    /* the only free in a resize */
    m->buckets = bigger;
    m->capacity = new_capacity;
    return 1;
}

Four things to notice. calloc, so every new slot starts as NULL. next is saved before n->next is overwritten, the same “save the rest, then change the thing you stand on” shape as lesson 10's reverse and free. The new index uses new_capacity, not m->capacity, which is still the old size until the last line. And there is exactly one free: the old array. A resize that calls strdup on each key, or malloc for each node, makes a second copy of something that already has an owner; valgrind then reports the originals as definitely lost (the cheat sheet has that report). Forget the one free and the old array leaks instead; that is optional experiment 4.

Because nodes never move, a pointer into a node survives a resize. That matters for the next function.

Get borrows; remove uses the slot

hashmap_get hashes, walks the chain, and returns the address of the value member inside the node it finds:

const int* hashmap_get(const hashmap_t* m, const char* key) {
    struct node* n = find_in(m->buckets[index_of(m, key)], key);
    if (n == NULL) {
        return NULL;
    }
    return &n->value;                                    /* borrowed: lives in the node */
}

That pointer is borrowed, exactly like lesson 12's bst_min. The node owns the int. The header says, in the same words as bst.h: the pointer is owned by the map and dies with hashmap_free, and also with hashmap_remove of that key, because remove frees the node. Reading through it after either call is a use-after-free; experiment 3 does it on purpose so you see the report once, as promised in lesson 12.

hashmap_remove is lesson 10's slot walk, started at the bucket instead of at l->head. The bucket slot and every next member are struct node*, so one struct node** reaches all of them and the first node of a chain needs no special case:

int hashmap_remove(hashmap_t* m, const char* key) {
    struct node** link = &m->buckets[index_of(m, key)]; /* the slot before the chain */
    while (*link != NULL && strcmp((*link)->key, key) != 0) {
        link = &(*link)->next;
    }
    if (*link == NULL) {
        return 0;                                        /* absent */
    }
    struct node* gone = *link;
    *link = gone->next;                                  /* the slot skips over gone */
    free(gone->key);
    free(gone);
    m->count--;
    return 1;
}

Two frees, in the order the ownership arrows run: the key copy is reached through the node, so it goes first. Remove mango from bucket 7 and link stops at the slot itself, &m->buckets[7]; remove apple and it stops at &mango->next. Same lines either way.

Free: key, node, array, struct

Four levels of ownership, released from the inside out. For each bucket, walk the chain with lesson 10's saved-next loop, freeing the key copy and then the node. Then the array. Then the struct:

void hashmap_free(hashmap_t* m) {
    if (m == NULL) {
        return;
    }
    for (size_t i = 0; i < m->capacity; i++) {
        struct node* n = m->buckets[i];
        while (n != NULL) {
            struct node* next = n->next;                 /* save before free */
            free(n->key);
            free(n);
            n = next;
        }
    }
    free(m->buckets);
    free(m);
}

Count the allocations in the test run: one struct, one 4-slot array, six nodes, six key copies, and one 8-slot array made by the resize. Fifteen. Fourteen die in hashmap_free; the 4-slot array died earlier, in hashmap_grow. valgrind reports 16 and 16, because printf allocates its buffer on the first call and frees it at exit.

The interface

hashmap.h

#pragma once

#include <stddef.h>

typedef struct hashmap hashmap_t;   /* opaque: the struct body lives in hashmap.c */

/* Create an empty map with a small bucket array. Returns NULL on allocation failure. */
hashmap_t* hashmap_new(void);

/* Free every key copy, every node, the bucket array, then the map. NULL is fine. */
void hashmap_free(hashmap_t* m);

/* Insert key with value, or overwrite the value if key is already present.
   The map stores its OWN copy of key (strdup); the caller keeps its string.
   Returns 1, or 0 if allocation failed: then no key was added and no value changed. */
int hashmap_put(hashmap_t* m, const char* key, int value);

/* Return a borrowed pointer to the value stored for key, or NULL if absent.
   The pointer is owned by the map and dies with hashmap_remove of that key
   and with hashmap_free. */
const int* hashmap_get(const hashmap_t* m, const char* key);

/* Remove key: frees the map's key copy and its node.
   Returns 1 if removed, 0 if key was absent. */
int hashmap_remove(hashmap_t* m, const char* key);

/* Number of keys in the map. */
size_t hashmap_count(const hashmap_t* m);

/* Number of buckets. Doubles when the map resizes. */
size_t hashmap_capacity(const hashmap_t* m);

Three functions change the map and take hashmap_t*. Three only read and take const hashmap_t*. Every key parameter is const char*: the function reads the caller's string and promises not to change it. hashmap_capacity exists so the test program can show the resize; a production header might leave it out. From <string.h> the exercise uses strcmp and strdup, both on the CS107 list; the sanitizer flags use gnu11 so that strdup, a POSIX function, is declared without extra macros.

Reading the reports

1. Signed hash. One line, before your output (paths trimmed; line numbers are yours):

hashmap.c:24:21: runtime error: signed integer overflow: 193502395 * 33 cannot be represented in type 'int'
after 3 puts: count 3, capacity 4
...

193502395 is the running total for pea; multiplying it by 33 for the r needs 33 bits. UBSan reports each source location once, so you see the first key that overflowed and no more. Every four-letter key does the same. The nine lines still come out right on both builds, because on this machine the overflow happened to wrap and the wrong hash was at least used consistently. Undefined behaviour does not promise a crash; it promises nothing. The compiler is allowed to assume an int never overflows and to optimise on that assumption. unsigned long removes the question.

2. Borrowed key. gcc says it first, because a const char* is being stored into a char* slot that the map intends to free:

hashmap.c:111:12: warning: assignment discards ‘const’ qualifier from pointer target type [-Wdiscarded-qualifiers]
  111 |     n->key = key;

Then the output is wrong before anything crashes:

after 6 puts: count 3, capacity 4
get fig: absent
get mango: 4

Six puts, three keys. Every node's key points at buf, so when apple arrived in bucket 3, find_in compared buf with buf, found a match, and overwrote fig's value; kiwi did the same to pear, mango to apple. No resize, because the count never passed 3. Now every node claims to hold whatever buf holds last, mango, which is why fig is absent and mango is found with a value. Then hashmap_free runs:

ERROR: AddressSanitizer: attempting free on address which was not malloc()-ed: 0x7a556d000020 in thread T0
    #0 in free
    #1 in hashmap_free hashmap.c:91
    #2 in main main.c:36

Address 0x7a556d000020 is located in stack of thread T0 at offset 32 in frame
    #0 in main main.c:18

  This frame has 1 object(s):
    [32, 48) 'buf' (line 24) <== Memory access at offset 32 is inside this variable
SUMMARY: AddressSanitizer: bad-free

The map freed main's stack. cppreference: “The behavior is undefined if the value of ptr does not equal a value returned earlier by malloc(), calloc(), realloc()”*. The plain build prints the same three lines and then dies with glibc's double free or corruption (out). The lesson is one sentence: a container that will call free on a pointer must be the one that called malloc for it, and strdup is how it does that for a string.

If you keep the full main instead of the short one, the first bad free is hashmap_remove freeing the literal "fig", and the sanitizer dies inside its own allocator with a less readable SEGV: string literals live, as Beej puts it, in “read-only memory”*, and even the sanitizer's bookkeeping cannot write there. Same bug, worse report; that is why the experiment uses the short test.

3. Borrowed value after remove. The plain build prints fig again: -1792341989 and exits 0: the allocator reused the first bytes of the dead node for its own bookkeeping, and the value member was inside them. A different machine prints a different number, or the stale 20. The sanitizer build tells the whole story:

ERROR: AddressSanitizer: heap-use-after-free on address 0x5030000000d8
READ of size 4 at 0x5030000000d8 thread T0
    #0 in main main.c:58                      ← the printf of *fig

0x5030000000d8 is located 8 bytes inside of 24-byte region
freed by thread T0 here:
    #0 in free
    #1 in hashmap_remove hashmap.c:145
    #2 in main main.c:57

    #0 in malloc

Read it bottom up. A 24-byte block, so a node, was allocated by the malloc in hashmap_put during the first put_range: that is fig's node, the second key. It was freed by hashmap_remove, called from the remove fig line. Then main read 4 bytes at offset 8, which is the value member after the 8-byte key pointer. The pointer fig carried that address across the free. make check says the same in valgrind's words: Invalid read of size 4 ... 8 bytes inside a block of size 24 free'd by hashmap_remove.

4. The resize that forgets. Nine correct lines, then:

==12345== 32 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x...: calloc
==12345==    by 0x...: hashmap_new (hashmap.c:73)
==12345==    by 0x...: main (main.c:29)

Four slots of 8 bytes: the first bucket array, born in hashmap_new, abandoned in hashmap_grow, which valgrind cannot name because the block was already unreachable when the program ended. The trace shows where a lost block was made; you supply where it was dropped. In this run the sanitizer build's LeakSanitizer reported it too, as “Direct leak of 32 byte(s)”; as NOTES records, it does not always, and make check is the gate.

A set is this map without the value

Delete the value member and the map becomes a set of strings: same hash, same chains, same key copies, same resize. hashmap_put becomes set_add and returns whether the key was new; hashmap_get becomes set_contains and returns 1 or 0, with no borrowed pointer to worry about. Nothing about ownership changes. It is not part of this exercise; if you want it, write it after lesson 14.

  1. Separate chaining in C, the textbook version. Mark Allen Weiss, Data Structures and Algorithm Analysis in C, 2nd ed., hashsep.h, hashsep.c and hashfunc.c, from the author's free source files. Three differences to find. His TheLists[i] is a header node allocated per bucket, so his Insert never writes the array slot and has no slot walk; yours has the slot walk and one allocation less per bucket. His table size is NextPrime of what you ask for and never changes; yours doubles. His keys are int, and the two comments “Probably need strcmp!!” in Find and “Probably need strcpy!” in Insert are exactly your find_in and your strdup. In hashfunc.c, Hash3 is djb2's shape: HashVal = (HashVal << 5) + *Key++ in an unsigned int. testhash.c is his test program: 400 inserts, then 400 finds that print only on failure.

  2. djb2 as it was posted. Ozan Yigit, Hash Functions. Half a page of C. The unsigned long accumulator, the (hash << 5) + hash form of “times 33”, Bernstein's later XOR variant, and the K&R first-edition function he calls “lose lose”, which is Weiss's Hash1: add the characters and hope. Read it to see why the multiply matters.

  3. The two rules you broke. cppreference, free, the paragraph of “The behavior is undefined if ...” sentences: passing a pointer that did not come from malloc (experiment 2) and accessing memory after free returns (experiment 3). Then the strdup entry of the CS107 C Standard Library Guide, three sentences on who must free the copy.

  4. If you prefer to watch first. CS50 Shorts, Doug Lloyd: Hash Tables. From Harvard's C-based introductory course. Hand traces of hashing, collisions and chaining, no ownership; the ownership part is this lesson's.

The chain-length claim and the doubling rule in the body cite Sedgewick and Wayne (3.4 Hash Tables, SeparateChainingHashST.java). Treat those links as evidence for a sentence, not as reading. Keep the cheat sheet for lookup. Next is lesson 14, the graph: the last lesson the mission requires, and it reuses lesson 11's queue unchanged.

Ask your teacher. Whenever a structure stores a pointer it did not allocate, ask who will free it and when the bytes behind it die. If the answer is “the caller, at some point”, the structure needs its own copy. And if a resize ever calls malloc or strdup inside its loop, stop and ask what the old block's owner is supposed to do now. Bring the bucket table for one key if the index arithmetic feels shaky; it is worth doing once by hand.
