The Slot Before the Node

A linked list is a chain of heap nodes. The head variable and every next member are slots of the same type, so one walk over slots inserts and deletes at the front, in the middle and at the end with no special case.

About 40 minutes Where: WSL, exercises/10-list/ Mission · Cheat sheet · Lesson 9
Your win today. Ship a singly linked list as an ADT: insert in order and remove by value through a node_t** walk that never asks “is this the head?”, reverse in place with three pointers, and free a chain without touching a dead block.

Where every byte lives

Two private structs live in list.c. The client sees neither. It holds a list_t* and nothing else, the same opaque struct arrangement as lesson 9's stack.

typedef struct node node_t;          /* private to list.c */

struct node {
    int     value;                   /* 4 bytes, then 4 bytes of padding */
    node_t* next;                    /* 8 bytes: the slot that leads onward */
};                                   /* 16 bytes per node */

struct list {
    node_t* head;                    /* the slot that leads to the first node */
    size_t  count;
};                                   /* 16 bytes, one per list */
An opaque struct is a struct whose members are declared only in the .c file. Clients can hold a pointer to it and pass that pointer back; they cannot read a member or compute sizeof. That is what forces every change to go through list_ functions.

After list_new and three pushes, the picture is this. One box in main's frame; everything else on the heap:

main's frame            heap
+---------+             +------------+      +-----------+      +-----------+      +-----------+
| l  o----+------------>| head  o----+----->| value  1  |   +->| value  3  |   +->| value  7  |
+---------+             | count  3   |      | next   o--+---+  | next   o--+---+  | next NULL |
                        +------------+      +-----------+      +-----------+      +-----------+
                          list_t              node_t             node_t             node_t

Ownership is one sentence long: main owns the list, and the list owns every node. main never sees a node, so it can never free one, so it can never free one twice. Sedgewick and Wayne define the structure recursively: a linked list “is either empty (null) or a reference to a node having a generic item and a reference to a linked list”*. In C, “reference” means node_t*, and the empty list is a head slot holding NULL.

Their traversal idiom carries over one for one*:

for (const node_t* cur = l->head; cur != NULL; cur = cur->next) {
    /* read cur->value */
}

That loop is enough for list_print. It is not enough for insert or delete, because those change an arrow, and to change an arrow you need the address of the slot that holds it.

The head is a slot, and so is every next

In lesson 4, words_find returned a char**: the address of a slot that held a char*. Writing *slot = copy changed which string the array held. Nothing else had to know which slot it was. Here the same idea appears at one level up. Give the pointers pretend addresses:

slot                 at address    holds        type of the slot    type of its address
l->head              0x500         0x610        node_t*             node_t**
(node 1)->next       0x618         0x620        node_t*             node_t**
(node 3)->next       0x628         0x630        node_t*             node_t**
(node 7)->next       0x638         NULL         node_t*             node_t**

Four slots. Each holds a node_t*. So the address of each one has type node_t**, whether the slot sits inside the list_t or inside a node. Beej makes the type step explicit: if p is an int*, then &p “is a pointer to an int*, AKA a ‘pointer to a pointer to an int’”*. Replace int with node_t and you have &l->head.

Now ask, for the sorted list 1 3 7, which slot must change to insert a value:

InsertGoes betweenSlot to changeAddress
53 and 7(node 3)->next0x628
0nothing and 1l->head0x500
97 and the end(node 7)->next0x638

Three positions, one kind of slot. So one loop finds it. Start at the slot before the first node, and move to the slot inside the current node until the node ahead is not smaller than v:

node_t** link = &l->head;                 /* the slot before the first node */
while (*link != NULL && (*link)->value < v) {
    link = &(*link)->next;                 /* the slot inside the node ahead */
}
Read &(*link)->next inside out. *link is the pointer stored in the slot: a node_t*. ->next reaches that node's next member. & takes the member's address. The parentheses are required: -> binds tighter than *, so *link->next would try link->next on a node_t**, and gcc stops with “‘link’ is a pointer to pointer; did you mean to dereference it before applying ‘->’ to it?”.

Trace it for v = 5:

link     *link            test          next step
0x500    0x610 (node 1)   1 < 5  yes    link = &(node 1)->next = 0x618
0x618    0x620 (node 3)   3 < 5  yes    link = &(node 3)->next = 0x628
0x628    0x630 (node 7)   7 < 5  no     stop; link is the slot that leads to 7

Splice in two lines, in this order:

node_t* n = node_new(v, *link);            /* n->next = the node ahead (7) */
if (n == NULL) {
    return 0;                              /* list unchanged */
}
*link = n;                                 /* the slot now leads to n */
l->count++;
before   [1]--->[3]--->[7]--->NULL
                    ^ link: the slot inside 3

after    [1]--->[3]--->[5]--->[7]--->NULL
                    ^ same slot, new arrow

Order matters. *link is the only path to node 7. The new node must take that path into its own next before the slot is overwritten. Write the slot first and the tail of the list is gone; experiment 3 shows what that looks like.

For v = 0 the loop body never runs, link is still 0x500, and *link = n writes l->head. For v = 9 the loop stops at 0x638 because *link is NULL; the new node gets next = NULL and the last slot leads to it. Same two lines. The head needs no if.

Delete by value with the same walk

Remove 5 from 0 1 3 5 7 9. The walk stops at the slot that leads to the node holding 5. That slot must skip over the node:

node_t** link = &l->head;
while (*link != NULL && (*link)->value != v) {
    link = &(*link)->next;
}
if (*link == NULL) {
    return 0;                              /* absent */
}
node_t* gone = *link;
*link = gone->next;                        /* the slot skips over gone */
free(gone);
l->count--;
return 1;
before   [3]--->[5]--->[7]
             ^ link

after    [3]---------->[7]        gone: [5] freed
             ^ link

Remove 0 and the walk stops at once with link == &l->head; the head slot skips to node 1. Same lines. The version most people write first has an if (l->head->value == v) path and a separate cur->next path. That is two places to call free and two places to decrement count, and one of them gets forgotten. Experiment 2 is that version.

Reverse with three pointers

Reverse 1 3 7 9 in place. Walk the chain once, flipping each arrow to point backwards. Flipping cur->next destroys the only path forward, so save it first:

node_t* prev = NULL;
node_t* cur = l->head;
while (cur != NULL) {
    node_t* next = cur->next;              /* save the rest */
    cur->next = prev;                      /* flip one arrow */
    prev = cur;                            /* advance both */
    cur = next;
}
l->head = prev;
prev    cur     next    after the flip
NULL    1       3       1->next = NULL
1       3       7       3->next = 1
3       7       9       7->next = 3
7       9       NULL    9->next = 7
9       NULL            head = 9          result: 9 7 3 1

No allocation, no free, count unchanged. A recursive reverse exists and is a good stretch (step 8), but each call is a frame on the C stack, one per node; the iterative form is the one to ship.

Free reads next before the block dies

The list owns every node, so list_free frees every node, then the list. Each node's next is the only path to the rest, and it lives inside the block about to die. Read it out first:

node_t* cur = l->head;
while (cur != NULL) {
    node_t* next = cur->next;              /* read before free */
    free(cur);
    cur = next;
}
free(l);

The tempting one-liner, for (cur = l->head; cur != NULL; cur = cur->next) free(cur);, evaluates cur->next after free(cur). cppreference states the rule: “The behavior is undefined if after free() returns, an access is made through the pointer ptr”*. Experiment 1 shows what gcc and AddressSanitizer say about it. The same “save the rest, then destroy” shape appeared in list_reverse; it is the shape of every loop that changes the thing it walks on.

The interface

list.h

#pragma once

#include <stddef.h>

typedef struct list list_t;

/* Create an empty list on the heap. Returns NULL if allocation fails. */
list_t* list_new(void);

/* Free every node, then the list itself. Consumes ownership. NULL is allowed. */
void list_free(list_t* l);

/* Insert v as the new first value. Returns 1, or 0 if allocation fails. */
int list_push_front(list_t* l, int v);

/* Insert v before the first value that is >= v. Keeps a sorted list sorted.
   Returns 1, or 0 if allocation fails (list unchanged). */
int list_insert_sorted(list_t* l, int v);

/* Remove the first node holding v. Returns 1 if removed, 0 if absent. */
int list_remove(list_t* l, int v);

/* Reverse the order of the nodes in place. No allocation. */
void list_reverse(list_t* l);

/* Print the values, space separated, on one line ending in a newline. */
void list_print(const list_t* l);

/* Number of values in the list. */
size_t list_count(const list_t* l);

Two functions take const list_t* because they only read. Inside them the walking pointer is const node_t* for the same reason. The invariants the .c must keep on every path: count equals the number of nodes, the last node's next is NULL, and no node is reachable from two slots.

Reading the three reports

1. Reading cur->next after free(cur). gcc 13 spots this simple form at compile time:

list.c: In function ‘list_free’:
list.c:42:50: warning: pointer ‘cur’ used after ‘free’ [-Wuse-after-free]
   42 |     for (node_t* cur = l->head; cur != NULL; cur = cur->next) {
list.c:43:9: note: call to ‘free’ here

Run it anyway and AddressSanitizer reports the read as a timeline: the access, the free, the allocation.

ERROR: AddressSanitizer: heap-use-after-free on address 0x5020000000d8 ...
READ of size 8 at 0x5020000000d8 thread T0
    #0 ... in list_free list.c:42
    #1 ... in main main.c:43
0x5020000000d8 is located 8 bytes inside of 16-byte region
freed by thread T0 here:
    #0 ... in free
    #1 ... in list_free list.c:43
previously allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in node_new list.c:19

A 16-byte region is one node. “8 bytes inside” is the next member: 4 bytes of value, 4 of padding, then the pointer. “READ of size 8” is a pointer being read. The warning catches only the pattern where the same variable is used; move the read through a second variable and gcc goes quiet, so the sanitizer run is still the check that counts.

2. A head special case that forgets. The program prints all nine lines, and the last one is wrong: count: 5 instead of count: 4. That is the missing decrement. The missing free shows under make check:

16 bytes in 1 blocks are definitely lost in loss record 1 of 1
   at 0x...: malloc
   by 0x...: node_new (list.c:19)
   by 0x...: list_insert_sorted (list.c:66)
   by 0x...: main (main.c:27)
LEAK SUMMARY:
   definitely lost: 16 bytes in 1 blocks
ERROR SUMMARY: 1 errors from 1 contexts

Valgrind names where the block was born, not where it was abandoned. The node holding 0 was created by list_insert_sorted; it was leaked by list_remove's head path, which is not in the trace at all. When a leak trace points at an allocation that looks correct, look for the path that dropped the pointer. In this run the ASan build's LeakSanitizer also reported “Direct leak of 16 byte(s)”; it does not always (see NOTES, LSan at -O0), which is why make check exists.

3. Writing the slot before taking its old value. The output is wrong from the second line on:

push: 1 3 7
sorted: 0 9
count: 6
remove 0: yes
remove 5: no
remove 4: no
after: 9
reversed: 9
count: 5

Inserting 5 pointed node 3's slot at a node whose next was NULL, so node 7 fell off. Inserting 0 did the same to the head slot, so the chain 1 3 5 fell off. count still says 6 because the increments ran. Valgrind counts the fallen nodes:

16 bytes in 1 blocks are definitely lost in loss record 3 of 4
   by 0x...: list_push_front (list.c:52)
48 (16 direct, 32 indirect) bytes in 1 blocks are definitely lost in loss record 4 of 4
   by 0x...: list_push_front (list.c:52)
LEAK SUMMARY:
   definitely lost: 32 bytes in 2 blocks
   indirectly lost: 32 bytes in 2 blocks
ERROR SUMMARY: 2 errors from 2 contexts

“Definitely lost” is a block nothing points to: node 7, and node 1. “Indirectly lost” is a block reachable only from a lost block: nodes 3 and 5, still hanging off node 1. One dropped arrow can lose a whole chain. The other order mistake, *link = n; followed by n->next = *link;, gives no message at all: n->next becomes n, the node points at itself, and the next walk never ends. If ./list prints push: 1 3 7 and then sits there, that is what happened; press Ctrl-C and check the two-line order.

Read next

Everything here is C, or has no code at all. Read in this order; the first item is the lesson's idea in someone else's words.

  1. The same walk, called “indirect”. Marc Kirchner, Linus Torvalds' linked list argument for good taste, explained. A short page with all the C. It comes from a 2016 TED interview (14:10) where Torvalds contrasts two ways to delete a node. remove_cs101 walks with prev and cur and ends in if (prev) ... else l->head = ...: that is experiment 2. remove_elegant declares list_item **p = &l->head, steps with p = &(*p)->next, and writes *p = target->next. “Indirect pointer” there means what link means here: the address of the slot, whether the slot is head or a next member. Two differences to notice. Their remove takes a node pointer, not a value, so the loop compares *p != target where yours compares (*p)->value != v. And it never calls free; the caller owns the node. Then read insert_before at the end and check it against your list_insert_sorted: same walk, same two-line splice.

  2. The classic alternative: a dummy header node. Mark Allen Weiss, Data Structures and Algorithm Analysis in C, 2nd ed., list.h, list.c and testlist.c (the author publishes the book's source files free). Weiss removes the head special case a different way: MakeEmpty mallocs one node that holds no value, and the real first node hangs off its Next. So “the slot before the first node” is always a node's Next, and a plain struct Node * can reach it. Compare Delete (fig 3.11) and FindPrevious (fig 3.12) with your slot walk: P->Next plays the part of *link, P->Next = TmpCell->Next; free(TmpCell); is your two lines, and the price is one extra node per list plus a header check in every function. Also read the #if 0 block: fig 3.14 is the “Incorrect DeleteList algorithm” that frees P and then reads P->Next, and fig 3.15 saves Tmp = P->Next first. That pair is experiment 1, printed in a textbook years before you hit it. Note that Weiss calls FatalError when malloc fails; you return 0 and leave the list unchanged.

  3. The first-course version, so you can count its branches. CS50x, Week 5 notes, the Linked Lists section. The same struct node { int number; struct node *next; }, then four full programs: prepend, print, append, sorted insert, and an unload that frees with a saved next. Read the sorted-insert program and count its cases: empty list, belongs at the front, append at the end, insert in the middle. Four writes to four differently named slots. Your list_insert_sorted has one write, *link = n, because it walks slot addresses instead of node pointers. If you prefer to watch first, CS50 Shorts, Doug Lloyd, Singly-Linked Lists, about sixteen minutes, C throughout.

  4. The two type facts the walk depends on. Beej, 23.1 Pointers to Pointers for the step from p to &p, which is the step from node_t* to node_t** in the slot table. Then 35.1 Use Case: Self-Referential Structures, one page on why struct node *next is legal inside struct node before the struct is complete; that is what makes typedef struct node node_t; in list.c work. 5.4 Passing Pointers as Arguments only if the copy-of-the-pointer rule needs a refresh.

Ask your teacher. If you ever write if (l->head->value == v) as a special case, stop and ask whether a slot walk removes it.
